# content-source/ —— 单元内容脚手架的**源文件**

这三份 JSON 是 `scripts/content/scaffold-unit.mjs` 的输入：**单元内容包的「源」**。
`content/` 下的 27 个包是**产物**（落盘形态），这里是**原料**。

```
content-source/unit-source-ielts-*.json   ← 源（人/PM 编辑，本目录）
        │  npm run content:scaffold-unit -- --src=<源> --check   （只校验，不写盘）
        │  npm run content:scaffold-unit -- --src=<源>            （落盘，⛔ 勿在 CI 跑）
        ▼
content/{vocabulary,reading,exercise}/ielts-*-{vocab,reading,exercise}/   ← 产物
```

## 为什么源要入库（2026-10-07）

在此之前源只在仓库外的 `D:/work/_ops/`，**CI 的任何 step 都不读那个目录**。
后果是 `scaffold-unit.mjs` 的判据 ①（「源缺 `license` 段就拒跑」）**在 PR 阶段形同虚设**——
它只在有人手动跑脚手架时才触发。而 CI 里真正生效的是 `content:validate` 的**盘侧**判据 23
（`content/` 里的包一旦被降级就判红），它守的是「降级不许落盘」，**不是**「源不许缺段」。

⇒ 源入库后，`content:validate` 的**判据 24**（源侧 fail-closed）才能在 CI 里常驻执行：
「源里声明了某段内容 ⇒ 必须显式声明该段 `license`」，缺段即红。

## 判据 24 与判据 23 的关系

**同一条规则的两个观测点，缺一不可，谁也不能替代谁。**

| | 判据 23（盘侧） | 判据 24（源侧） |
|---|---|---|
| 守什么 | 已落盘的包**不许被降级**（棘轮） | 源**不许缺段**（fail-closed） |
| 在哪 | `content/*/*/manifest.json` | 本目录 `*.json` |
| 只有它没有对方 | 源合规但盘上被手改降级 ⇒ 漏 | 盘是对的，但「下次跑脚手架就会降级」的定时炸弹没人看见 ⇒ 漏 |

证伪自检（证明门会判红、且不是恒红门）：

```bash
npm run content:validate -- --falsify
```

## 判据 25 / 26 / 27（2026-10-07 补齐的三条覆盖缺口）

| | 守什么 | 为什么需要它 |
|---|---|---|
| **25** | 源 ↔ 磁盘**一致性**（载荷 + manifest 除 build 戳外逐项比对） | 24 只查 license 段声明，**看不见词条/段落被改**。这件事原先只由 CI 的 `scaffold-unit --check` 那一步负责，而那一步只以「deploy.yml 里有某一行」的形式生效 —— 删掉它就静默失守。25 把同一事实搬进**门禁本体** |
| **26** | 源 ↔ 包 ↔「谁该有源」**三方对账** | 24/25 都只从**已存在的源**出发。若有人落了盘却忘了把源入库，两条都看不见 ⇒「这个包由哪个源生成」变成不可知，下次没人能还原它 |
| **27** | 段类型**单一真源上锁** | 「可声明哪几段」此前是**两份字面量**，只靠注释互指。改一处忘另一处 ⇒ 两层口径分叉且**无人发现** |

### 判据 25 与 CI 那步 `--check` 的关系（**重要**）

**同一事实、两个观测点、一份实现：**

- 事实只有一个：「入库的源能否还原磁盘上现有的包」。
- 观测点 1 = CI 的 `scaffold-unit --check` 那一步（逐条 ✓/✗，给人看）。
- 观测点 2 = 判据 25（门禁内，与其它判据同一份 FAIL 汇总）。
- **实现只有一份**：`scripts/content/unit-source-render.mjs` 的 `planUnitSource()` + `comparePackageToDisk()`。
  ⛔ 门禁**不会** import `scaffold-unit.mjs`（那是带 CLI 的脚本，import 即触发 `process.exit` / 真写盘 ——
  本仓明令禁止「测试与门禁 import 生成器」），所以渲染与比对被抽成了**无副作用的纯模块**供两边共用。
- **两步都保留**：CI 那步给人看；判据 25 保证「删掉那步也不丢覆盖」。

### 判据 26 为什么不需要人工维护「预期源清单」

判据 26 要回答「哪些包应该有源」，但 ⛔ **不维护任何硬编码名单** —— 名单本身就是新的漂移源
（加包要记得改，忘了又是一道新病）。它改为**现场派生**：
包 id 形如 `<prefix><dirSuffix>` 且 `<dirSuffix>` ∈ 段表的 `dirSuffix` 集合 ⇒ 该包应有源。

实测（27 个包）：恰好 **9 个**命中（`ielts-{edu-01,env-02,tech-03}` × `{vocab,reading,exercise}`），
13 个词汇小包（`ai-core`/`cet4`/`kaoyan`/…）与 8 个 `demo-*` **全部不命中** ⇒ **零误伤**。
加第 4 个单元**不需要改任何名单**：包一落盘就自动进入对账范围。

⚠️ **已知且刻意接受的假阳性面**：若将来有人**手工**造一个恰好叫 `xxx-vocab` 的非脚手架包，
它会被判成「该有源而没有」。宁可多问一句「这个包由哪个源生成」，也不要让无源的脚手架形态包静默存在。
真要豁免请**改包名**，⛔ 不要在判据里加白名单（白名单就是那份被禁止的人工清单）。

### 判据 27 的证伪注入（本轮核心验收）

证伪里真的把唯一真源的段列表**改少一个（去掉 `exercise`）**，断言「口径被改动」被机器判据抓住
（判据 27b 的**手写字面真值**），而不是靠人看注释。

它还如实记录了一个**被实测证伪出来的真实假绿**：段表改小后，判据 26 会把那 3 个 `*-exercise` 包
**排除出对账范围**而误判绿（`problems=0`）—— 这正是 27b 必须存在的原因。
证伪断言 4b 把这个盲区钉在案：将来若判据 26 改成能兜住，这条断言会红并提醒更新说明。

## ⛔ 这个目录**不是**内容包根

`content:validate` / `content:ingest` 扫描的是 **`content/`**，不是仓库根。
所以本目录**不会**被当成内容包扫描。反过来，**别把源放进 `content/`**：

```bash
# 实测（复现「源放错位置 ⇒ 判红」）：
cp content-source/unit-source-ielts-edu-01.json content/          # → 静默忽略（是文件不是目录）
mkdir -p content/unit-source && cp …/edu-01.json content/unit-source/   # → ✗ 未知内容类型目录 ⇒ FAIL
```

## ⚠️ 改动纪律

- **纯移动，不许顺手改**：源文件入库时逐字节原样搬运（`.gitattributes` 对本目录标了 `-text`，
  因为 `unit-source-ielts-tech-03.json` 实际带 CRLF，被 git 归一后本地与 CI 拿到的就不是同一份字节）。
- 改源 ⇒ 必须跑 `content:validate`（判据 24）+ 下面这条 `--check`。
- ⛔ **不要**为了让 `--check` 变绿去改 `content/` 下的包：**磁盘现状是基准**，
  源与盘不一致时要先判断「谁错了」，而不是无脑迁就任何一侧。
