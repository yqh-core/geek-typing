## 1. 四条红线（给审计方与后续维护者）

这一节是本文件的重点。以下四件事**必须是显式约定**，而不是"大家都懂"：

### 🔴 红线 1：绝不能把 GitHub 上的素材直接塞进网站

**原因**：

| 问题 | 说明 |
|---|---|
| GitHub 仓库**不等于**可自由使用的素材 | 一个仓库里放着词表，不代表作者授权你使用它。**无 LICENSE 文件 = 保留全部权利**（默认版权） |
| 词表类素材的权属**极其复杂** | 词表常常是"从某词典抓的"，上传者自己没有权利，无法转授给你 |
| "能下载到" ≠ "能用" | 技术可获取性与法律可用性完全无关 |
| **词典释义受版权保护** | 词典的释义文字是受保护的创作性表达。逐条抄录释义与整本复制在版权上差别很小 |
| 追溯困难 | 一旦上线，内容会被搜索引擎索引、被用户导出、被 PWA 缓存到用户设备 —— **下架不等于消失** |

**正确流程**：

```
发现一个看起来合适的词表（GitHub / 网盘 / 论坛 / 论文附录）
  ↓
1. 查 LICENSE 文件
   ├─ 有明确许可（MIT / CC0 / CC-BY 等）→ 核对是否覆盖"数据"（很多 LICENSE 只覆盖代码）
   ├─ 无 LICENSE → ❌ 停止，视为"保留全部权利"
   └─ 有 LICENSE 但含糊（"仅供学习"） → ❌ 停止，需人工法务判断
  ↓
2. 查内容本身的来源
   ├─ 仓库明确说明数据来自 XXXX 且有 XXXX 的授权 → 记录完整证据链
   └─ 仓库没说数据从哪来 → ❌ 停止（上传者可能自己都没有权利）
  ↓
3. 记录证据链（sourceUrl / author / copyright / downloadDate）
  ↓
4. 设 rightsStatus（cleared / pending / unavailable）
  ↓
5. 只有 rightsStatus === 'cleared' 才能进 content/
```

**当前这道流程没有任何机制保障。** `scripts/content/validate.mjs` 第 7 项只检查"`sources[]` 里有没有 license 对象" —— **如果有人直接填一个 `{"name": "MIT License", "spdx": "MIT"}` 而实际来源不明，门禁会放行。**

### 🔴 红线 2：ECDICT 的 MIT 许可必须核实覆盖范围

**这是一个需要人工核实、不能假定的事项。**

实测：5 个包（9153 词）声明 `origin: "ECDICT"` + `license: MIT` + `spdx: "MIT"` + `url: https://opensource.org/licenses/MIT`。

**需要核实的三件事**：

| # | 待核实项 | 为什么 |
|---|---|---|
| 1 | ECDICT 的 MIT 许可**是否覆盖词表数据本身**，还是只覆盖代码 | 很多项目的 LICENSE 只针对代码，数据另有条款 |
| 2 | ECDICT 里的释义**本身从哪来**（若 ECDICT 也是从别处整合的，它的 MIT 声明可能无权转授） | **"整合型"数据集最容易有这个问题** |
| 3 | 是否有任何附加条款（如"不得用于商业词典产品"） | 上游的 README 常有 LICENSE 之外的限制说明 |

**⚠️ 必须强调**：本文件的实测只能证明"仓库里声明了 MIT"，**不能证明"这个 MIT 声明有效覆盖了所有 9153 条词条"**。这是一个**法律判断，需人工核实 ECDICT 上游仓库的 LICENSE 与 README**，不是工程能单独结论的。

**为什么这条特别值得警惕**：

| 事实 | 含义 |
|---|---|
| ECDICT 词数 **9153**，占全库 9346 词的 **97.9%** | **风险高度集中在这一个来源** |
| 3 个 lazy 包（ielts/kaoyan/toefl）各 3000 词，合计 9000 词 | 单点风险 |
| `attributionRequired: false` 这个布尔值**是我们自己填的** | **它不是 ECDICT 对我们的承诺**，是我们的理解 |

**最后一条很关键**：`attributionRequired: false` 是我们写进 manifest 的**判断**，不是上游给的字段。如果这个判断是错的，那么我们的部署就缺少了必要的署名。

**⇒ 建议动作：人工登录 ECDICT 的上游仓库，逐字核对 LICENSE 与 README，并把核对结果（含核对日期、核对人）记录到 `sources[]` 的 `copyright` / `downloadDate` 字段。**

### 🔴 红线 3：curated 包的 "Proprietary" 声明必须名副其实

实测 5 个 curated 包（193 词）声明：

```json
"origin": "curated in-repo (云原生词库)",
"license": { "name": "Proprietary (self-curated)", "commercialUse": true, "attributionRequired": false }
```

**"self-curated"（自研）的声明必须核实**：

| 风险 | 说明 |
|---|---|
| 词条可能是从别处抄的 | 如果"云原生词库"的 30 条词和释义是从某个技术词典抄的，**它不是 self-curated** |
| 释义文字可能有第三方来源 | 词（`kubernetes`）无版权，但**释义文字可能有** |
| 技术术语的译法可能来自某标准化组织 | 通常无版权问题，但值得确认 |

**当前这 5 个包很简单**（20~50 词，都是技术术语，如 `cloud-native` 30 词、`frontend` 20 词），**实际风险很低**。但**声明与事实的一致性**必须成立 —— 如果这些词的释义确实抄自某词典，"Proprietary (self-curated)" 就是虚假声明。

**⇒ 建议动作：对 5 个 curated 包逐包确认释义来源，并在 `sources[]` 里记录"释义由本项目编写"这一事实。**

### 🔴 红线 4：不要把"能跑起来"当成"能上线"的充分条件

**这是一条工程与法律的边界约定。**

| 门禁能证明 | 门禁**不能**证明 |
|---|---|
| JSON 格式合法 | 内容来源合法 |
| checksum 一致 | 内容有权使用 |
| 有 license 字段 | license 声明是**真的** |
| 有 SPDX 标识 | SPDX 标识**适合**这个内容 |
| 体积在预算内 | 内容没有侵权 |

**⇒ 门禁是必要条件，不是充分条件。上线前必须有人对"内容权利"做实质判断。**

**当前的状态是**：门禁很强（20 项），但它**完全无法阻止**"把一个来源不明的词表填个 MIT 就上线"这件事。这是审计报告里必须点明的**能力边界**。

## 2. ECDICT 覆盖度核实（实测）

### 2.1 实测数据

| 项 | 值 |
|---|---|
| ECDICT 派生包数 | **5**（ielts / kaoyan / toefl / cet4 / cet6） |
| ECDICT 派生词数 | **9153** |
| 占全库比例 | **9153 / 9346 = 97.9%** |
| curated 包数 | 5 |
| curated 词数 | **193**（43+30+20+50+50） |
| 占全库比例 | **2.1%** |

**⇒ 全库几乎完全由一个来源（ECDICT）支撑。** 这是一个**高风险的单点依赖**：

- 若 ECDICT 的许可判断有误 ⇒ **97.9% 的内容面临风险**
- 若 ECDICT 上游变更许可 ⇒ 影响同一比例
- 无法通过"换掉一小部分"来缓释

### 2.2 ECDICT 词条的实际字段（实测样本）

以 ielts 包第一条为例：

```json
{
  "word": "eagle",
  "translation": "n. 鹰, 鹰状标饰",
  "phonetic": "'i:gl",
  "definition": "n. any of various large keen-sighted diurnal birds of prey noted for their broad wings and strong soaring flight"
}
```

**关键观察：`definition` 是英文释义，且具有明显的"词典释义"特征。**

| 字段 | 版权分析 |
|---|---|
| `word` | 单个英文单词，**无版权**（事实性元素） |
| `phonetic` | 音标，**无版权**（事实性元素） |
| `translation` | "n. 鹰, 鹰状标饰" —— 简短释义，**创造性有限，但仍是表达** |
| `definition` | **一段完整的英文释义文字** —— **这是最需要关注的字段** |

**`definition` 字段是最需要警惕的**：

- 完整的句子、有措辞选择、有组织方式 ⇒ 属于**受版权保护的表达**
- 若 ECDICT 的这段释义来自某版权词典（如 WordNet 或商业词典），**ECDICT 的 MIT 声明可能无权覆盖它**
- 这正是红线 2 的第 2 条（"ECDICT 里的释义本身从哪来"）的具体体现

**⚠️ 注**：ECDICT 上游通常是整合多个来源（部分可能来自 WordNet 等开放数据源）。**是否所有 `definition` 都可自由使用，必须核实，不能假定。**

### 2.3 覆盖度与完整性的其他风险

| # | 风险 | 实测 |
|---|---|---|
| 1 | **CET 覆盖严重不足** | `CONTENT-001`：cet4 **84 词 ≈ 1.9%**、cet6 **69 词 ≈ 1.3%**（相对真实 CET 词表规模） |
| 2 | **9163 条缺 example / audio / pos** | `CONTENT-003`，占 98% |
| 3 | **7 个包字段贫瘠** | `CONTENT-002` |
| 4 | **BUG-001**：`helpline` 的 `definition` 为空串 | 而 `manifest.stats.definition = 2999` 的口径是"**key 存在**"而非"值非空" |

**风险 4 的许可含义有限，但它暴露了一个模式**：**统计数据反映的是"字段存在"，不是"内容质量"**。同样的模式可能存在于许可声明上 —— **"有 license 字段"不等于"许可有效"**。

**这是一个值得审计方注意的类比**：本项目的元数据校验普遍是"结构校验"而非"实质校验"。这在工程上是合理的（工程不该做法律判断），**但必须在文档里明确这个边界，否则会给人"许可已经核查过了"的错觉。**

## 4. 一个必须说清的非风险：跨包同词

**2323 处跨包同名词形不是内容风险，是刻意设计。**

`scripts/content/validate.mjs` 第 4 项注释原文：

> **跨包同词合法**：IELTS/CET/TOEFL 各有 abandon 是正常数据关系，是本平台刻意支持的能力，**任何「跨包词唯一」规则都是错误的**

**审计时不要把"同一个词在多本词书里出现"当成内容重复或数据污染。** 这就像"同一个汉字在多本教材里都有" —— 是正常的。

**但有一个真实的衍生风险**（`A-4`，架构问题而非许��问题）：

> Learning 层用**裸 word** 做键 ⇒ 2323 处跨包同词会导致**学习记录串包**（在 ielts 里学过的 `abandon`，到 cet4 里显示已学）

**这是架构缺陷（`A-4`），不是版权问题。** 列在这里只是为了避免审计方把它误判为内容问题。

## 5. 下架流程的缺失（P-1 / P-2）

### 5.1 为什么"下架"比想象中难

标准流程是"从 `content/` 删掉那个词库，重新部署"。**但对本项目不够**，因为有 Service Worker：

| 层 | 下架后会发生什么 |
|---|---|
| 服务端 | ✅ 新部署不再包含该内容 |
| CDN | ✅ 边缘缓存会随部署更新 |
| **用户浏览器 HTTP 缓存** | ⚠️ `/assets/*` 是 `immutable` **一年**！ |
| **用户 SW 的 Cache Storage** | ⚠️ **旧 chunk 仍在用户设备上** |
| **已安装的 PWA** | ⚠️ 离线时仍会用旧缓存 |

**关键问题**：lazy 包的 words 是 `words-*.js`（在 `/assets/` 下）：

- `public/_headers`：`/assets/*` → `Cache-Control: public, max-age=31536000, immutable`
- `public/sw.js`：`/assets/*` → **cache-first**

⇒ **一个已被用户加载过的词库 chunk，会在用户设备上保留整整一年。下架在生产环境生效，但在用户设备上不生效。**

### 5.2 真正的下架流程（建议）

```
1. 从 content/vocabulary/ 删除该包
2. 【关键】修改 public/sw.js 的 CACHE 版本号（gt-shell-v2 → gt-shell-v3）
   —— 这会触发 activate 清理所有旧缓存
3. 重新构建、部署
4. 验证：用 prod-smoke Part B 思路（模拟旧版本残留）确认清理生效
5. 记录：下架原因、时间、原始来源（以备后续申诉）
```

**第 2 步是必须的，也是最容易被遗漏的** —— 不升版本号，SW 的 `activate` 不会清理，用户的旧缓存会一直服务。

**这与 `12-infrastructure/DISASTER_RECOVERY.md` §3.2 的 SW 应急流程是同一个机制**（`CACHE` 版本号硬编码在 `public/sw.js`）。

### 5.3 需要建立的流程文档

| # | 文档 | 内容 |
|---|---|---|
| 1 | **来源审核清单** | 见 §1 红线 1 的五步流程 |
| 2 | **证据记录规范** | 每引入一个来源必须记录的字段（sourceUrl / author / copyright / downloadDate / rightsStatus） |
| 3 | **下架流程** | 见 §5.2 五步（**必须含 SW 版本号升级**） |
| 4 | **投诉响应流程** | 谁接收、多久响应、如何核实、如何处置 |
| 5 | **定期复核计划** | 每年复核一次上游许可是否变更 |

**第 4 条尤其重要**：本项目**无隐私政策页、无联系邮箱、无关于页**（实测 `index.html` 只有 title/description/keywords/author 元信息）。若有人要投诉侵权，**找不到提交渠道** —— 这在法律上会把"善意使用"变成"怠于处置"。

## 8. 一句话总结给审计方

**许可元数据是真实的（10 包、含 SPDX、结构规范），但内容风险集中且具体：97.9% 的词（9153/9346）来自 ECDICT 单一来源，其中 `definition` 字段是完整的英文释义段落、属于受版权保护的表达，而"ECDICT 的 MIT 是否覆盖这些释义"**尚未核实**——且 manifest 里的 `attributionRequired: false` 是我们自己填的判断而非上游承诺，这个判断若错则部署缺少必要署名。第二条现实缺口是 MIT 要求分发时随附版权声明与许可全文，而仓库内无 `LICENSE`、`sources[]` 无 `copyright`/`sourceUrl`、站内无归属页，三者皆无（补齐成本极低）。第三条是流程完全缺失：没有任何机制阻止"直接把 GitHub 上的素材填个 MIT 就塞进网站"，而门禁第 7 项只查字段存在性、不查声明真伪——这是它的能力边界，必须写清而不是给人"已核查"的错觉。第四条容易被忽略：**下架比想象中难**，因为 `/assets/*` 是 `immutable` 一年 + SW cache-first，一个已被加载的词库会在用户设备上保留一年，真正的下架必须同时升级 `public/sw.js` 的 `CACHE` 版本号以触发清理。另外站点无隐私政策页、无联系渠道，侵权投诉无处提交，这在法律上会从"善意使用"变成"怠于处置"。**
