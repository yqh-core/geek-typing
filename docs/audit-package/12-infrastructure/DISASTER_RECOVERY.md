## 2. 好消息：这个项目的架构天然降低了 DR 难度

需要如实指出——**纯静态站是 DR 最友好的形态**：

| 特性 | DR 收益 |
|---|---|
| **无数据库** | 无数据损坏/主从切换/一致性恢复问题 |
| **无服务端状态** | 无 session、无队列、无需恢复进程 |
| **无上传文件** | 无对象存储备份问题 |
| **全部内容在 git** | 内容与代码同源、同版本、可完整重建 |
| **可重复构建** | `npm ci && npm run build` 可在任何机器上重建产物 |
| **用户数据在客户端**（localStorage） | 服务端无用户数据可丢 |

**推论：最坏情况下的恢复动作就是"从 git 重新构建并部署"。** 这是 DR 里最简单的情况。

**但前提是 git 可访问。** 所以真正需要预案的是：**git 不可用 / GitHub 不可用 / Cloudflare 不可用**这几种情况。

## 3. 故障场景与预案

### 3.1 场景矩阵

| # | 场景 | 影响 | 当前能否应对 | 需要什么 |
|---|---|---|---|---|
| F-1 | **一次部署引入了 bug** | 全站功能异常 | ⚠️ 理论上能（平台回滚），**但无流程文档** | 回滚操作说明 |
| F-2 | **内容包数据错误** | 部分词库异常 | ✅ 能（改内容重新部署） | 内容回滚流程 |
| F-3 | **SW 版本导致离线白屏** | 部分用户断网不可用 | ⚠️ **难**（见 §3.2） | SW 版本回滚流程 |
| F-4 | **Cloudflare Pages 故障** | 全站不可用 | ❌ **不能** | 备用托管 / 静态快照 |
| F-5 | **GitHub 不可用** | 无法部署（站点仍在线） | ⚠️ 部分（有 `dist` 可手动传） | 手动部署说明 |
| F-6 | **域名问题** | 无法访问 | ❌ 不能 | 注意：用的是平台子域，无自有域名可控 |
| F-7 | **构建依赖被删/被投毒**（npm registry 问题） | 无法构建 | ⚠️ 部分（有 lockfile） | 依赖缓存 / vendor 快照 |
| F-8 | **`content/` 目录误删** | 内容丢失 | ✅ 能（git 恢复） | 无（git 即备份） |
| F-9 | **Secret 泄露/失效** | 无法部署 | ⚠️ 部分（有自检） | Secret 轮换流程 |

### 3.2 F-3 是最难的一个场景（值得单列）

**为什么 SW 回滚比普通代码回滚难**：

Service Worker 是**持久化在用户设备上**的。即使你在服务端把 `sw.js` 换回旧版本：

1. 用户浏览器里**当前的 SW** 仍是新版本（`gt-shell-v3`）
2. 它会继续用 `gt-shell-v3` 缓存服务页面
3. **它的 `activate` 逻辑会删掉所有非 `gt-shell-v3` 的缓存** ⇒ 你部署的"旧版本"（如 `gt-shell-v2`）的缓存会被立刻删掉
4. 用户不会被降级

**即：SW 的错误版本会在用户设备上"坚守"，除非**：
- 发布一个**新版本号**（如 `gt-shell-v4`）的 SW，且它修正了问题
- 用户手动清除站点数据

**当前 `public/sw.js` 的版本号是硬编码常量**：

```js
const CACHE = 'gt-shell-v3'
```

⇒ **修复流程必须是"升版本号"而不是"回退版本号"**。这个约束**没有任何文档记录**。

**这是一个真实的运维陷阱**：出问题时工程师的第一反应是"回滚到上一个提交"，但对 SW 来说回滚可能无效甚至加剧问题（回滚后的 SW 版本号与用户设备上的相同，浏览器会认为"没有新版本"而不更新）。

**建议的 SW 应急流程**：

```
1. 确认问题在 SW 层（用户报"断网白屏"）
2. 不要回滚代码 —— 而是在坏版本基础上发布 NEW 版本号（gt-shell-v3）
3. 新版本必须：
   a. 用新 CACHE 名（触发 activate 清理）
   b. 修正导致问题的逻辑
   c. 保留 skipWaiting + clients.claim（保证快速生效）
4. 验证：prod-smoke Part B（含注入旧版本残留的 B3 测试）
```

**关键洞察**：`tests/prod-smoke.mjs` 的 **B3** 恰好就是"注入 `gt-shell-v1` 残留 → 重装 → 清理 → 断网可用"的验证 —— **这套测试天然就是 SW 升级路径的演练**。应急流程应当直接复用 B3。

### 3.3 F-4：Cloudflare Pages 故障

**当前完全无应对能力。** 可能的预案：

| 方案 | 成本 | 效果 |
|---|---|---|
| 保存一份 `dist` 静态快照 | 极低 | 可上传到任何静态托管（Netlify / Vercel / GitHub Pages / 对象存储） |
| 双托管（CF + 备用） | 中 | 需要 DNS 切换能力 |
| **但注意**：当前用的是平台子域 `*.pages.dev` | — | **无法通过 DNS 切换**（域名不属于项目） |

**这是一个结构性弱点**：`https://geek-typing.pages.dev/` 是 Cloudflare 拥有的域名空间（`pages.dev`）。项目**没有自有域名**，因此：
- 无法做 DNS 级 failover
- 无法真正"迁移平台"而不改 URL
- URL 变更会破坏：`index.html` 的 `canonical`、PWA manifest、已安装的 PWA 图标、用户书签

**若要具备真正的 DR 能力，第一件事是绑定自有域名。** 这是一项前置条件，不是可选的优化。

### 3.4 F-7：依赖供应链

| 现状 | 事实 |
|---|---|
| 有 lockfile | ✅（`npm ci` 依赖它，CI 也用 `npm ci`） |
| 运行时依赖数 | **4 个**（react / react-dom / lucide-react / canvas-confetti） |
| 依赖快照 | ❌ 无 |
| `npm audit` 接入 | ❌ 无 |

**lockfile 保证"能装到同一个版本"，但不保证"那个版本还能从 registry 下载到"**（如包被 unpublish、registry 故障）。

**预案建议**：把 `node_modules` 的构建产物（即 `dist/`）作为发布物归档。因为**本项目最终产物是纯静态文件**——只要保留一份可用的 `dist/`，就不需要重新构建。

## 4. 待建方案

### 4.1 最小可行 DR（成本低、见效快）

| # | 事项 | 成本 |
|---|---|---|
| 1 | 写一份**回滚操作说明**（Cloudflare Pages 控制台路径 + 命令） | 1 页文档 |
| 2 | 写一份 **SW 应急说明**（强调"升版本号而非回退"，含 `gt-shell-v3` 流程） | 1 页文档 |
| 3 | 建立 **`dist` 归档**（每次部署后保留产物，至少保留 N 份） | 少量脚本 |
| 4 | 写一份**故障响应清单**（谁看什么、怎么判断、怎么通知） | 1 页文档 |
| 5 | 定义 **RTO / RPO** | 半页文档 |

**RTO / RPO 建议**（供讨论）：

| 项 | 建议值 | 依据 |
|---|---|---|
| **RPO** | **0**（无数据可丢） | 无服务端数据；内容在 git；用户数据在客户端 |
| **RTO（代码回滚）** | < 15 分钟 | Cloudflare Pages 回滚是控制台操作 |
| **RTO（SW 应急）** | < 30 分钟 | 需要改版本号 + 重新部署 + 等用户端更新 |
| **RTO（平台级故障）** | **当前不可达** | 无备用托管、无自有域名 |

**注意 RPO = 0 的论证**：这是纯静态站的结构性优势。应该明确写出来——**大多数系统的 DR 难点在数据，这个系统的数据在 git 和用户浏览器里，都不依赖运行时基础设施**。

### 4.2 演练建议

| # | 演练 | 频率 |
|---|---|---|
| D-1 | 回滚一次部署（在 staging 或选低峰期） | 每季度 |
| D-2 | SW 应急流程演练（发布 `gt-shell-v3`） | 每半年 |
| D-3 | 从零构建验证（干净 clone → `npm ci` → `build` → 部署到临时环境） | 每半年 |
| D-4 | 模拟平台故障（用 `dist` 归档到别的托管起一个实例） | 每年 |

**D-2 可以直接复用 `tests/prod-smoke.mjs` 的 B3**（注入旧版本残留 → 验证清理），因为它已经验证了升级路径的核心逻辑。

**D-3 已在 CI 里被部分覆盖**：`deploy.yml` 与 `e2e.yml` 都在干净环境跑 `npm ci && npm run build`，所以"从零构建可行"这件事**已经被持续验证**。这是一个意外的 DR 收益。

### 4.3 结构性改进

| 优先级 | 事项 | 说明 |
|---|---|---|
| 🔴 P0 | **绑定自有域名** | **这是 DR 能力的前置条件** —— 无自有域名则无法做任何 DNS 级故障切换 |
| 🟠 P1 | 启用 Cloudflare Pages Preview 分支 | 同时解决"无 staging"（`DEPLOYMENT.md` §5）与"无演练场地" |
| 🟡 P2 | 备用托管方案（`dist` 归档） | 对应 F-4 |

**"绑定自有域名"排在最前面是有理由的**：当前 `geek-typing.pages.dev` 是平台子域，项目对 URL 没有控制权。这不只是一个 DR 问题——它也意味着：
- 无法迁移平台而不破坏所有链接
- `canonical` URL（`index.html` 里写的是 `https://geek-typing.pages.dev/`）随平台变化
- 已安装 PWA 的用户会因 URL 变更而失效

**对于任何要长期运营的产品，自有域名是基础设施的基本要求。**

## 5. 与测试体系的关系（一个正面观察）

**这个项目的测试体系已经提供了部分 DR 价值，只是没有以 DR 的名义组织起来：**

| 测试 | 隐性 DR 价值 |
|---|---|
| `tests/prod-smoke.mjs` Part B（B1/B2/B3） | **SW 升级路径验证** —— 直接对应 F-3 应急预案 |
| `tests/prod-smoke.mjs` Part A（A1~A5） | **线上健康检查** —— 可直接用作部署后验证与 uptime 探测的基础 |
| `tests/offline-audit.mjs`（5 态，20 项断言） | 离线可用性验证 —— 对应"断网白屏"类事故 |
| `deploy.yml` 的干净构建 | **持续验证"从零构建可行"** —— 对应 D-3 |
| `content:validate`（20 项） | 内容完整性验证 —— 对应 F-2 / F-8 |

**即：DR 缺的不是"验证能力"，而是"流程与文档"。** 已有的测试脚本可以直接复用为应急预案的验证步骤。

**建议**：写 DR 文档时**直接引用这些测试命令作为验证步骤**，而不是另起一套。

## 7. 一句话总结给审计方

**DR 完全空白（无备份策略、无回滚文档、无演练、无 RTO/RPO），但架构本身让这个问题的严重性大幅降低：纯静态、无数据库、无服务端状态、无上传、内容全在 git、构建可重复、用户数据在客户端——最坏情况的恢复动作就是"从 git 重新构建并部署"，RPO 实质为 0。真正的风险集中在四处：一是 SW 版本回滚的陷阱（`CACHE` 版本号是硬编码常量，回退代码无效甚至加剧问题，必须升版本号，而这一点无任何文档）；二是只有一个生产环境且无回滚说明；三是用的是平台子域 `*.pages.dev`，项目对 URL 无控制权，因此**无法做任何 DNS 级故障切换**——绑定自有域名是获得 DR 能力的前置条件；四是依赖供应链无快照。一个正面观察是：缺的不是验证能力（`prod-smoke` 的 B3 天然就是 SW 升级演练，`deploy.yml` 的干净构建已持续验证"从零构建可行"），而是流程与文档。**
