# 监控（Monitoring，待建）

> 状态：📐 待建
> 已有断言数：**0**
> 实测结论：**零监控。无埋点上报、无错误收集、无性能采集、无可用性探测、无告警**

---

## 1. 实测现状

### 1.1 零服务端监控

| 能力 | 现状 |
|---|---|
| 错误上报（Sentry / 自研） | ❌ 无 |
| 性能采集（Web Vitals 上报） | ❌ 无 |
| 访问统计（GA / Plausible / Umami） | ❌ 无 |
| 可用性探测（uptime check） | ❌ 无 |
| 告警（邮件 / IM / PagerDuty） | ❌ 无 |
| 结构化日志 | ❌ 无（纯静态站，无服务端） |

**实测确认**：`grep -rn "sentry\|analytics\|gtag\|plausible\|umami\|reportError"` 在 `src/` 与 `index.html` 中**零命中**（除 `src/lib/analytics.ts` 这个本地统计模块，见 §1.2）。

### 1.2 `src/lib/analytics.ts` 是本地统计，不是监控

**这是一个必须澄清的点**，避免审计方误判"已经有 analytics 了"：

| 项 | 事实 |
|---|---|
| 文件 | `src/lib/analytics.ts` |
| 数据去向 | **仅存 localStorage** |
| 是否上报 | ❌ **不上报任何服务端** |
| 用途 | 结算页展示"本轮/历史"数据（WPM 趋势、正确率） |

它是**面向用户的功能**（给用户看自己的进步），**不是面向运维的监控**（给团队看服务是否健康）。

**区别的实际后果**：

| 问题 | 本地 analytics 能否回答 |
|---|---|
| 用户 WPM 有没有提高 | ✅ 能（用户自己看） |
| 有多少用户在用 | ❌ **不能** |
| 哪个功能崩了 | ❌ 不能 |
| 首屏加载慢了没有 | ❌ 不能 |
| 有多少人断网后白屏 | ❌ 不能 |
| SW 升级成功率多少 | ❌ **不能** |

### 1.3 `tests/_evidence/` 是审计快照，不是持续监控

`tests/_evidence/` 下有：

```
01-intro.png
02-quiz.png
03-result.png
04-mobile.png
offline-audit-result.json
```

这些是**测试运行时落盘的证据**，是**一次性的快照**，不构成监控（无时间序列、无对比基线、无告警）。

对应 `PERF-002`（无性能监控基线）。

### 1.4 唯一的"可观测性"：CI 部署日志

| 来源 | 内容 | 保留 |
|---|---|---|
| GitHub Actions 运行日志 | 构建是否成功 | GitHub 默认保留期 |
| Cloudflare Pages 控制台 | 部署历史、请求量（平台侧） | 平台策略 |

**注意**：Cloudflare Pages 平台**确实提供**基础的请求分析（PV、带宽、错误率）。所以严格说不是"绝对零监控"——但是：

- **项目内没有任何配置或使用**这些平台能力
- **没有任何告警规则**
- **没有人被指派去看**

即：**平台提供了仪表盘，但没有任何流程在使用它。**

## 2. 零监控的实际风险（结合已知问题）

这是本节最重要的部分——**把所有已知问题映射到"如果当时有监控会不会更早发现"**：

| 已知问题 | 如果有监控 |
|---|---|
| **三类静默 `ERR_FAILED`**（`public/sw.js` 的 `sanitize` 注释） | 🔴 **能在第一时间发现**。这是典型的生产事故：部分用户断网白屏。有错误上报的话，`ERR_FAILED` 会立刻出现在错误列表里 |
| **cet4/toefl/ielts 共用 namespace ⇒ abandon 三包同 id** | 🟠 不能（这是数据问题，不是运行时错误）。但它说明**有些问题只能靠门禁** |
| **`BUG-001` `helpline` definition 空串** | 🟡 数据质量问题，监控帮不上 |
| **`CONTENT-001` CET 覆盖不足（1.9% / 1.3%）** | 🟡 同上 |
| **`FLAKY-001` 本地/线上产物不一致** | 🟢 监控能间接发现（线上指纹变了） |
| **`UX-002` 词库加载失败无反馈** | 🔴 **能在第一时间发现**：加载失败会抛错，错误上报会抓到，且能看到影响多少用户 |
| **`PERF-001` 主 chunk 余量 9.3%** | 🟠 监控能发现"首屏变慢"，但不能直接发现"体积涨了"（需要构建产物上报） |
| **`UX-001` 无离线状态 UI** | 🟡 体验问题，监控量化不了 |
| **`A-4` Learning 用裸 word 做键，2323 跨包同名词** | 🔴 **能发现**：如果上报"学习记录异常"（如记录数暴涨、跨包污染），能定位到这个问题 |
| **`O-3` 缓存配额耗尽** | 🔴 **能发现**：`QuotaExceededError` 上报 |

**结论：三类静默 `ERR_FAILED` 与 `UX-002` 这两个问题，如果有错误监控，本可以在生产环境第一时间被发现，而不是靠人工读代码注释。**

**其中 `sanitize()` 的存在本身就是证据**——它存在是因为**曾经踩过坑**。如果当时有监控，这个坑的发现与定位成本会低一个数量级。

## 3. 待建方案

### 3.1 分层建议（从零成本到完整）

#### 第 0 层：平台能力（零成本，立即可做）

| 项 | 做法 |
|---|---|
| Cloudflare Pages 自带分析 | 在 Cloudflare 控制台确认已启用，并**指定人定期看** |
| 部署失败通知 | GitHub Actions 的失败邮件默认开启，确认有接收人 |
| 部署后自动冒烟 | 在 `deploy.yml` 最后跑 `test:smoke`（见 `DEPLOYMENT.md` §8） |

**这一层不写任何代码，但能覆盖"部署是否成功"与"站点是否活着"。**

#### 第 1 层：错误监控（最高性价比）

**推荐用 `window.onerror` + `unhandledrejection` + 自建上报端点，或用现成服务（Sentry 的免费额度足够）。**

必收字段：

| 字段 | 用途 |
|---|---|
| 错误消息 + stack | 定位 |
| URL / 路由 | 定位 |
| 用户代理（浏览器/OS/版本） | 环境区分 |
| SW 状态（`navigator.serviceWorker.controller` 是否存在） | **离线相关问题的关键** |
| 在线状态（`navigator.onLine`） | 同上 |
| 缓存的 SW 版本（`gt-shell-v3`） | **版本升级问题定位** |
| 时间戳 | 时序 |
| 会话 ID（本地生成，匿名） | 聚合 |

**为什么要收 SW 状态与在线状态**：因为本项目最难的 bug（三类 `ERR_FAILED`）**全部只在特定 SW/网络状态下出现**。不收这两个字段，错误上报会变成"大量不明 ERR_FAILED"，无法定位。

#### 第 2 层：Web Vitals 上报

| 指标 | 采集方式 | 上报时机 |
|---|---|---|
| FCP | `PerformanceObserver` | 页面隐藏时（`visibilitychange` → `hidden`） |
| LCP | 同上 | 同上 |
| TTFB | Navigation Timing | 同上 |
| CLS | 同上 | 同上 |
| INP | 同上 | 同上 |

**为什么在页面隐藏时上报**：避免占用首屏资源（本项目主 chunk 余量仅 9.3%，任何额外代码都要谨慎）。

**建议字段**：附上部署版本（可从 `index.html` 里的 bundle hash 提取），这样才能做**版本间的性能对比**。

#### 第 3 层：业务事件（可选）

| 事件 | 用途 |
|---|---|
| 词库加载成功/失败（含包名、耗时、错误类型） | 对应 `UX-002` |
| SW 安装/激活/升级（含版本号） | SW 健康度 |
| 缓存配额异常 | 对应 `O-3` |
| 打字会话开始/结束（WPM 分桶，**不上报具体输入内容**） | 产品指标 |
| 自定义词库导入 | 对应上传能力（见 `UPLOAD_SECURITY.md`） |

**隐私注意**：打字练习涉及用户输入内容。**绝不能上报用户的按键内容或自定义词库原文**（自建词库可能含用户隐私）。只上报**聚合数值**（WPM、时长、字符数）。

#### 第 4 层：可用性探测（uptime）

| 项 | 建议 |
|---|---|
| 探测目标 | `https://geek-typing.pages.dev/` |
| 频率 | 5 分钟 |
| 判据 | HTTP 200 且 HTML 含 `<div id="root">`（**不能只看 200**——白屏也返回 200） |
| 告警 | 连续 2 次失败 → 通知 |

**"不能只看 200"这一条很重要**：`tests/preview-server.mjs` 的探针就是这么做的（检查首页含 `<div id="root">`），说明项目里已经有正确的探针判据，只是没用在生产监控上。

### 3.2 告警规则建议

| 规则 | 阈值 | 严重度 |
|---|---|---|
| 站点不可用 | 连续 2 次探测失败 | 🔴 P0 |
| 错误率突增 | 错误数 > 基线 3 倍 | 🔴 P0 |
| `ERR_FAILED` 出现 | 任意非零 | 🔴 P0（**这是本项目最该告警的错误类型**） |
| 首屏 LCP P75 | > 2.5s 持续 30 分钟 | 🟠 P1 |
| SW 激活失败率 | > 5% | 🟠 P1 |
| 部署失败 | 任意 | 🟠 P1 |
| 词库加载失败率 | > 1% | 🟠 P1（对应 `UX-002`） |

## 4. 隐私与合规考量

这是"零监控"现状下的一个**意外优势**，需要如实指出：

| 项 | 现状 |
|---|---|
| 无 Cookie（除 localStorage 的功能性存储） | ✅ |
| 无第三方追踪脚本 | ✅ |
| 无 IP 收集 | ✅ |
| 无用户数据外发 | ✅ |

**引入监控会新增隐私面**，需要考虑：

| 问题 | 建议 |
|---|---|
| 是否需要 Cookie 同意横幅？ | 若只做自研匿名上报且不含个人数据，多数法域下可豁免；用第三方 SaaS 则通常需要 |
| IP 是否算个人数据？ | 多数法域下算（GDPR 明确）。建议**服务端不落 IP 或立即匿名化** |
| 自建词库内容是否会上报？ | **绝不能**（见 §3.1 第 3 层的隐私注意） |
| 是否需要隐私政策页面？ | 当前站点无隐私政策页（见 `11-legal/`），引入监控前应先补齐 |

**即：引入监控不只是技术工作，还有合规前置条件。**

## 5. 与 CI 门禁的关系（重要区分）

**监控不能替代门禁，门禁也不能替代监控。** 两者覆盖不同的问题：

| 问题类型 | 门禁能抓 | 监控能抓 |
|---|---|---|
| 内容不合规（namespace 撞车） | ✅ | ❌ |
| 体积超预算 | ✅ | ❌ |
| **线上 CDN 配置被改错** | ❌（本地测不到） | ✅ |
| **特定浏览器/网络下的 SW 失败** | ❌ | ✅ |
| **真实用户的首屏性能** | ❌（本地无网络延迟） | ✅ |
| **缓存配额耗尽** | ❌ | ✅ |
| 版本升级导致的回归 | 部分 | ✅ |

**本项目的门禁很强但都没进 CI（`DEBT-002`），监控为零。** 两者同时缺失意味着：**生产环境的真实状态目前完全不可见。**

## 6. 优先级建议

| 优先级 | 事项 | 成本 | 理由 |
|---|---|---|---|
| 🔴 **P0** | **启用并定期查看 Cloudflare Pages 自带分析** | 零代码 | 已有的能力，只是没人用 |
| 🔴 **P0** | **部署后自动跑 `test:smoke`** | 少量 YAML | "部署的东西是活的"这件事目前无人确认 |
| 🔴 **P0** | **错误监控（含 SW 状态 + 在线状态字段）** | 中等 | 三类 `ERR_FAILED` 与 `UX-002` 都属于"有监控就能早发现" |
| 🟠 P1 | 可用性探测（判据必须含 `<div id="root">`） | 低 | 白屏也能返回 200 |
| 🟠 P1 | `ERR_FAILED` 专项告警 | 低 | 本项目最该告警的错误类型 |
| 🟠 P1 | Web Vitals 上报（页面隐藏时发） | 中等 | 主 chunk 余量紧，需谨慎控制体积 |
| 🟡 P2 | 业务事件（词库加载成败） | 中等 | 对应 `UX-002` |
| 🟡 P2 | 补齐隐私政策页 | 低 | 引入监控的合规前置 |
| ⚪ P3 | 缓存配额异常监控 | 低 | 对应 `O-3` |

## 7. 一句话总结给审计方

**监控为零：无错误上报、无性能采集、无访问统计、无可用性探测、无告警。需要注意 `src/lib/analytics.ts` 容易造成误判——它是本地写 localStorage 的用户功能（给用户看自己的 WPM），不是监控，数据一个字节都不出浏览器。零监控的代价是具体的：本项目最难的三类静默 `ERR_FAILED`（`sanitize()` 的存在就是为了修它们）与 `UX-002`（词库加载失败无反馈）都属于"有错误监控就能在生产第一时间发现"的问题。零监控也带来一个意外好处——当前没有任何第三方追踪脚本、无 IP 收集、无数据外发，引入监控需要先补齐隐私政策并明确不上报用户输入内容。**
