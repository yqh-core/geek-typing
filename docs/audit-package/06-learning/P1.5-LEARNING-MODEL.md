## 0. 一句话结论

**Learning 层升级的本质不是「把 key 换成 ContentId」，而是把「用户学到什么程度」这件事从「一个可能有歧义的字符串」重新挂到「一个无歧义的实体标识」上；全库 6713 个不同 word 里有 2323 个（34.6%）的裸 word 在当前 10 包体系下无法唯一映射，这批记录的归属信息在写入旧键的那一刻就已经永久丢失 —— 因此迁移方案的核心不是「猜得准」，而是「不猜、可解释、可回滚、且孤儿档必须真实可数」。**

## 1. (a) `LearningRecord` 设计

### 1.1 现网四类 Learning 键的真实形状（`[读码]` 全部亲自核对）

| 存储键 | 声明位置 | 键 | 值类型 | 写入失败行为 |
|---|---|---|---|---|
| `gt.review.v1` | `reviewStore.ts:27` | **原词形**（保留大小写） | `ReviewEntry` | `console.warn` + 返回 `SaveResult` |
| `gt.memorize.v1` | `memorizeStore.ts:16` | **原词形** | `MemRecord` | `catch {}` 静默 |
| `gt.analytics.v1` | `analytics.ts:6` | `letters` = `letter.toLowerCase()`（`:60`）；`words` = `word.toLowerCase()`（`:73`） | `Analytics` | `catch {}` 静默（`:48`） |

### 1.2 目标类型：完整 TS 接口

```ts
/**
 * Learning 层的一等公民：**一条 LearningRecord = 一个 ContentId 的学习状态**。
 *
 * 三层边界（model/content.ts:3-7 定版）：
 *   Content  —— 内容是什么（不随用户变）
 *   Learning —— 用户与某条内容的互动状态（本类型）
 *   User     —— 用户画像与偏好
 *
 * ⚠️ 本类型**只承载「挂得到某条 content 上的状态」**。
 *    任何全局性、与具体 content 无关的聚合（字母统计、总击键数、最佳 WPM）
 *    一律不进本类型 —— 见 §1.3 的拆分论证。
 */
export interface LearningRecord {
  /** 主键，4 段式：content:<type>:<namespace>:<localId>（model/content.ts:9-14） */
  contentId: string
  /** 学的是该实体的哪个版本（对外学习契约号；进 ContentId 会断链，见 model/content.ts:164-166） */
  contentVersion?: number
  /** 规范化内容指纹（canonical SHA-256），与 contentVersion 互补而非冗余（model/content.ts:182-188） */
  contentChecksum?: string
  /** 版本健康度：由 §1.4 的判定规则写入，供 UI 与诊断消费 */
  freshness?: LearningFreshness
  /** SRS / 错题状态（对应旧 ReviewEntry，字段一一对应、不重算） */
  review?: LearningReview
  /** 背单词掌握状态（对应旧 MemRecord） */
  memorize?: LearningMemorize
  /** 词级学习分析（对应旧 analytics.words[k] —— **不含 letters**） */
  analytics?: LearningAnalytics
}

/** 与 reviewStore.ReviewEntry 字段完全一致 —— 迁移只改键，不改值（MIGRATION_AUDIT §4.1） */
export interface LearningReview {
  wrongCount: number
  correctStreak: number
  lastWrongAt: number
  nextReviewAt: number
  /** 0..4，索引进 INTERVALS_DAYS = [1,2,4,7,15]（reviewStore.ts:25） */
  intervalIdx: number
}

/** 与 memorizeStore.MemRecord 字段完全一致 */
export interface LearningMemorize {
  status: 'known' | 'fuzzy' | 'unknown'
  reviews: number
  lastAt: number
}

/** 对应旧 analytics.words[k]（WordStat），键由 lowercase 换成 ContentId */
export interface LearningAnalytics {
  done: number
  wrong: number
}

/**
 * 版本健康度：
 *   ok      —— contentVersion / contentChecksum 与当前内容包一致
 *   stale   —— contentVersion 落后于当前包（内容修订过），**复习记录仍有效**，只是排期依据可能过时
 *   drifted —— contentChecksum 不匹配（内容实质变了），需用户确认后才继续沿用
 *   unknown —— 旧迁移记录未写入版本三元组（`legacy:` 前缀记录永久为此态）
 */
export type LearningFreshness = 'ok' | 'stale' | 'drifted' | 'unknown'

/** 新存储键的顶层形状 */
export type LearningStoreV2 = Record<string, LearningRecord>   // key = contentId
```

### 1.3 `analytics.letters` 的处置 —— 结论：**拆出去，不进 LearningRecord**

**为什么硬塞是错的（三条独立理由，任一条成立即可否决）**：

1. **语义错配（最根本）**。`letters` 的 26 个键是 `'a'..'z'`，它们**不是 content**。ContentId 的 4 段式要求 `type` 属于 `ContentType` 联合（`model/content.ts:34-46`），共 12 个成员，**没有也不应该有 `letter`**。要塞进去只有两条路：给 `ContentType` 加一个 `'letter'`（污染内容模型，且字母不是「内容包」）、或者用非规范的伪 id（如 `letter:a`）。两条都是给一个**非内容**的东西套内容的外衣。
2. **基数与生命周期完全不同**。`letters` 的 26 个键**永不过期、永不删除、与用户学到哪条内容无关**；而 `LearningRecord` 会因为「毕业」（`recordCorrect` 走完 15 天档位后条目被移除，`reviewStore.ts:135-142`）而被删除。把字母统计放进会被删除的记录里，等于让「统计面板的字母弱项」随错题本毕业而随机归零 —— 这是**明确的功能回归**。
3. **迁移语义不同**。`words` 表迁移需要做「lowercase 键 → ContentId」的**重建**（§1.3.2）；`letters` 表**什么都不用做**（键是单字母，`letter.toLowerCase()` 对 `'a'..'z'` 是恒等变换，`analytics.ts:61` 的 `/^[a-z]$/.test(key)` 已经把非字母键全部丢弃）。两者走同一个迁移分支是**多余的耦合**。

**目标拆分**：

```ts
/** src/lib/letterStats.ts —— 独立存储键 'gt.letterStats.v1' */
export interface LetterStats {
  /** 26 个键固定为 'a'..'z'（恒为小写，无大小写语义问题） */
  letters: Record<string, { hit: number; miss: number }>
}

/**
 * 全局聚合统计 —— 独立存储键 'gt.totals.v1'
 * 这四项**天然不属于任何一条 content**：totalKeys 是击键数、totalCorrect 是正确击键数、
 * totalWords 是完成词次、bestWpm 是单轮最佳 —— 都是「跨 content 的累加量」，
 * 归属到任意一个 ContentId 上都是错的（且迁移会重复计数：一条记录只能存一份聚合）。
 */
export interface GlobalTotals {
  totalKeys: number
  totalCorrect: number
  totalWords: number
  bestWpm: number
}
```

**迁移动作（`letters` 与全局标量）**：从 `gt.analytics.v1` 里**原样搬运**到新键，键名不变、值不变、不做任何计算。`gt.analytics.v1` 迁移后**只剩一个空的骨架**，由迁移脚本在报告里标 `deprecated`（§2.2）。

### 1.4 `contentVersion` / `contentChecksum` 的写入与过时判定

**写入时机（三个，缺一不可）**：

| 时机 | 写什么 | 从哪取 |
|---|---|---|
| 迁移时（旧记录有 `resolved` 映射） | `contentVersion` = 当前包的 `manifest.contentVersion`；`contentChecksum` = 当前包的 `manifest.contentChecksum` | `PackageManifest`（`schema.ts:56,67`） |
| 迁移时（`legacy:*` 记录） | **两者都不写**，`freshness = 'unknown'` | —— |
| 运行时首次学习/复习某条 content | 若记录尚无版本字段，补写当时的 `manifest.contentVersion/contentChecksum` | 同上的 manifest |

> **为什么不给 `legacy:*` 记录写版本**：`legacy:unattributed:<word>` 的候选有 N 个包、每个包的 `contentVersion` 可能不同（`[实测]` 10 包的 `contentVersion` 均为 1，但这是**当前**快照，未来会分化）。给一个「不知道属于谁」的记录写一个「某个包的版本号」，就是**制造假精度** —— 与 C4「不猜」原则直接冲突。故写 `freshness: 'unknown'`，这是诚实的表达。

**过时判定规则（纯函数，无副作用，可在 UI 侧随时调用）**：

```ts
/**
 * 判定一条 LearningRecord 相对当前内容包新鲜度。
 * @param rec        Learning 记录
 * @param manifest   该 contentId 所属包的当前 manifest（null = 包已不存在）
 * @returns freshness（不修改 rec；调用方决定是否回写）
 */
export function judgeFreshness(
  rec: Pick<LearningRecord, 'contentVersion' | 'contentChecksum'>,
  manifest: Pick<PackageManifest, 'contentVersion' | 'contentChecksum'> | null,
): LearningFreshness {
  // ① legacy:* / 未写版本 → unknown，永不做任何自动判定
  if (rec.contentVersion == null && rec.contentChecksum == null) return 'unknown'
  // ② 包已不在（词条被移除，但记录还在）→ drifted：内容源没了，比 stale 更严重
  if (manifest == null) return 'drifted'
  // ③ checksum 不匹配 → 内容指纹变了（改释义/改音标/改例句都算），需用户确认
  if (rec.contentChecksum != null && rec.contentChecksum !== manifest.contentChecksum) return 'drifted'
  // ④ version 落后但 checksum 一致 → stale：契约号过期，内容其实没变
  if (rec.contentVersion != null && rec.contentVersion < manifest.contentVersion) return 'stale'
  return 'ok'
}
```

**各档位的业务处理（这是判定规则真正落地的地方）**：

| freshness | 复习排期 `nextReviewAt` | 错题计数 `wrongCount` | UI 展示 | 自动动作 |
|---|---|---|---|---|
| `ok` | 有效，照常调度 | 有效 | 正常 | 无 |
| `stale` | **有效**（排期是时间维度，与内容修订无关） | 有效 | 加一个极淡的「内容已更新」标记 | 无（下次学会时自动补写新 version） |
| `drifted` | 有效 | 有效 | 显式提示「该词释义已更新，是否重置进度？」 | **不自动重置** —— 用户可能就是要保留 |
| `unknown` | 有效（`legacy` 记录照常参与总错题数统计） | 有效 | 归入「未归属」分区（§2.4.4） | 无 |

> **一个必须明确的判定边界**：`contentChecksum` 不匹配**不代表学习记录失效**。用户在旧释义上练了 10 次，这 10 次是真实发生过的历史，不会因为释义更新而消失。`drifted` 只影响「是否需要让用户重新确认这条词的学习意义」，不影响「计数」。任何把 `drifted` 记录**自动删除或自动重置**的实现都是**静默删用户数据**，禁止。

### 1.5 复合键边界：同一 word 在 3 个包 = 3 条 LearningRecord —— 正确吗？

**结论：正确，且是本次升级的**全部意义所在。

**论证（三层）**：

1. **契约层**：`content:word:ecdict-ielts:abandon` 与 `content:word:ecdict-kaoyan:abandon` 是**两个不同的内容实体**。`model/content.ts:16-23` 明确写：「跨包同词是**合法数据关系**（IELTS/CET/TOEFL 各有 abandon），消歧手段是 namespace 而不是禁止同词」。既然是两个实体，各自持有一份学习状态就是**唯一自洽的模型**。
2. **业务层**：用户在 IELTS 包里练 `abandon`、在考研包里也练 `abandon`，这是两个不同的备考场景。用户可能 IELTS 那本已经滚瓜烂熟、考研那本还一塌糊涂。旧模型下这两个进度**共享一个 `"abandon"` key、互相覆盖** —— 这是**真实的进度污染**，不是理论问题。新模型下它们天然隔离。
3. **规模层**：`[实测]` 这不会让存储爆炸。全库「记录条数 9346 / 唯一 word 6713」，而 localStorage 是 **map，重名同词物理上只会有一个键**（EVIDENCE-INDEX §10.3 已修正这个口径）。升级后一个键变成「每个候选包一个键」，最坏是 `abandon` 从 1 个键变成 5 个键（`generalize` 的实测是 5 包）。**但注意：只有用户真的在多个包里学过同一个词才会分裂**。用户全库压测 S7（EVIDENCE-INDEX §10.2）假设的是「6713 个 word 各学一遍」，升级后的体积 §2.9 实测为 3.894 MiB，在配额内。

**必须同时承认的代价（这是设计的一部分，不是缺陷）**：

| 代价 | 说明 | 缓解 |
|---|---|---|
| 体积膨胀 | 1.40×（§2.9 实测） | 配额充足（38.97%），不需要额外优化；但**必须进 release gate 的实测项** |
| 「总错题数」语义变化 | `reviewTotal`（`App.tsx:193`）从「不同词数」变成「(词,包) 对数」 | UI 文案改为「复习条目」，且增加「去重后词数」副指标；去重成本 = 在 records 上按 `localId` 分组 |
| `App.tsx:252` 的 `reviewSingleWord` 会退化 | 它用 `bankWords.find(w => w.word.toLowerCase() === word.toLowerCase())` 找词，跨包同名会**取到第一个** | 升级为 `findByContentId(contentId)` 精确取（§3.7 迁移路径第 5 步） |

## 2. (b) Migration v1 设计

### 2.1 迁移源：5 个键逐个定性

| # | 旧键 | 含词？ | 是否迁移 | 目标 | 理由 |
|---|---|---|---|---|---|
| 1 | `gt.review.v1` | ✅ 键 = 原词形 | **迁移** | `gt.learning.v2[id].review` | 核心 SRS 数据 |
| 2 | `gt.memorize.v1` | ✅ 键 = 原词形 | **迁移** | `gt.learning.v2[id].memorize` | 掌握度数据 |
| 3 | `gt.analytics.v1` | ⚠️ **部分**：`words` 含词；`letters` 与 4 个标量**不含** | **拆两份迁** | `words` → `gt.learning.v2[id].analytics`；`letters` → `gt.letterStats.v1`；4 标量 → `gt.totals.v1` | 见 §1.3 |
| 4 | `gt.customBanks.v1` | ✅ `CustomBank.words: WordItem[]` | **不动词，只建索引**（见下） | `gt.customBankIndex.v1` | 见 §2.1.1 |
| 5 | `gt.streak.v1` | ❌ 键 = `'YYYY-MM-DD'` | **不迁移** | —— | `streak.ts:19-23` 的 `todayKey()` 生成日期键，`DayRecord` 只有 `{date, words, seconds}`，**一个词都不含**。它与 Learning 层**完全正交**，升级 ContentId 对它零影响。**明确结论：`gt.streak.v1` 不在迁移范围内，迁移脚本读取时应当直接跳过并在报告中标 `not-applicable`。** |

#### 2.1.1 `gt.customBanks.v1` 的处理 —— 一个容易做错的点

**关键澄清**：自定义词库里的 `WordItem` 是**用户导入的原始内容**，它**没有**、也**不会有** ContentId —— 因为它不属于任何已发布的 content package（`PackageManifest` 里没有它的条目）。所以：

- **`CustomBank.words` 的存储形状不变**（仍是 `WordItem[]`，`customBanks.ts:8`）。给它们强行编 ContentId 会违反 `namespace 必须每包唯一` 的契约（`model/content.ts:16-23`），且用户下次编辑词库时 id 会变，学习记录全部断链。
- **需要迁移的是「用户在这个自建库里练过哪些词」这个关联**。旧模型下，用户在自建库里练 `abandon` 会写进 `gt.review.v1['abandon']`，与内置包**完全混淆、无法区分**。升级后应当区分。
- **本轮不实现自建库的 ContentId 化**（那需要先给自建库定 namespace 规则，属 P2）。**本轮只做**：迁移时为每个 `CustomBank` 生成一个索引条目：

```ts
/** gt.customBankIndex.v1 —— 自建库的 ContentId 空间占位（本轮只建索引，不迁学习记录） */
export interface CustomBankIndexEntry {
  bankId: string                  // 'custom-m1x2y3'（customBanks.ts:28 的生成格式）
  /** 建议 namespace：'custom-' + bankId 去掉 'custom-' 前缀的 base36 部分（每库唯一） */
  namespace: string
  /** 该库当前的词形快照（原词形，保留大小写；用于与 Learning 记录做交叉判定） */
  words: string[]
  createdAt: number
}
export type CustomBankIndex = Record<string, CustomBankIndexEntry>   // key = bankId
```

**为什么本轮不做自建库的完整 ContentId 化（要论证，否则是偷懒）**：

1. **namespace 唯一性契约要求每包唯一**（`model/content.ts:17-18`）。自建库的 `id` 是 `custom-${Date.now().toString(36)}`（`customBanks.ts:28`），**天然唯一且不会与内置包撞**（内置包 namespace 形如 `ecdict-*` / `curated-*`）。所以 namespace 规则本身很简单。
2. **但 `localId` 稳定性契约会破**（`model/content.ts:25-30`）：localId 一旦发布即成为永久主键，**不得因展示文本变化而修改**。用户**随时可以编辑自建库**（重新导入、改释义、删词）。「用户可以改自己的内容」与「localId 永久稳定」是**直接冲突**的。
3. 因此自建库要做对，需要一个**独立的 localId 生成策略**（例如内容 hash 而非词形），这属于**另一个设计任务**（P2），塞进 P1.5 会让本次迁移的范围失控。
4. **本轮的正确边界**：自建库的**学习记录**按 §2.3 的三档规则**统一进入 `legacy:*` 或 `resolved`**（因为裸 word 无法判断它来自内置包还是自建库）—— 这是诚实的：**我们不知道这条记录属于自建库还是内置包**，所以不猜。索引条目为 P2 的「让用户逐条认领」留出数据基础。

### 2.3 三档迁移语义（复用 `migration-audit.mjs` 定义，落到**动作**）

三档的**判据完全复用**审计脚本 `classifyKey`（`scripts/learning-consistency.mjs` §2 逐键分类，`migration-audit.mjs` 同样口径）：

```ts
function classifyKey(word: string, content: ContentTruth): Tier {
  const exact = content.wordToPkgs.get(word)          // Map<string, string[]>
  const lower = content.lowerToPkgs.get(word.toLowerCase())
  if (!exact && !lower) return 'orphan'
  if (!exact && lower) return 'caseConflict'          // 大小写口径冲突 → 单列一档（见 §2.3.5）
  if (exact.length >= 2) return 'ambiguous'
  return 'resolved'
}
```

| 档 | 数量 | 占比 | 动作 |
|---|---|---|---|
| `resolved` | **4390** | 65.4% | 直接写 `content:word:<ns>:<word>` |
| `ambiguous` | **2323** | 34.6% | 写 `legacy:unattributed:<word>`（§2.4） |
| `orphan` | **N/A → 由迁移时算出真实值** | —— | 写 `legacy:orphan:<word>`（§2.5） |
| `caseConflict` | `[实测]` 真实语料 **0**（`contentCaseCollisions = 0`）；合成数据 91 | —— | 见 §2.3.5 |

> `[实测]` 说明：`contentCaseCollisions = 0` 是我本轮用 `wordToPkgs` / `lowerToForms` 重建后亲自算出（`contentCaseCollisions = 0` / `lowerToPkgs distinct = 6713` / `wordToPkgs distinct = 6713`，两者相等正是 0 冲突的直接原因）。EVIDENCE-INDEX §11 的 `caseConflict = 91` 是**合成数据注入的 dirty sample**（`scripts/learning-consistency.mjs` 的 `buildSynthetic()` 用 `analyticsWords[w.toLowerCase()]` 造键），**不代表真实语料有此问题**；它量化的是「一旦真实用户数据里有大写原词，analytics 的 lowercase 键必然匹配不上」这件事的规模。

### 2.4 `ambiguous`（2323 条）：三方案对比与选定

**问题的本质（必须先说清，否则方案对比没有依据）**：旧记录 `gt.review.v1['abandon']` 里**只有一个裸字符串**。它对应的 `ReviewEntry` 有 `{wrongCount, correctStreak, lastWrongAt, nextReviewAt, intervalIdx}`（`reviewStore.ts:14-20`）—— **没有任何字段携带「包」这一维**（没有 `bankId`、没有 `namespace`、没有时间戳能反查到当时的包选择）。信息在写入那一刻就已经丢失。三个方案的差别**不在「能不能恢复」**（都不能），而在「**丢失的那一维如何表达**」。

| 方案 | 做法 | 副作用 | 结论 |
|---|---|---|---|
| **① 全部保留到 `legacy:unattributed:<word>` 占位档** | 2323 条原样保留数值，归属显式标为「未归属」，候选清单内联 | ① UI 需要新增「未归属」分区，且有下游过滤成本（§2.4.4）；② 用户会看到「2323 条记录没有归属」 | ✅ **选定** |
| **② 按「用户当前选中的 bank」猜** | 读 `gt.bank`（`App.tsx:91`），把该包作为归属 | ① **`gt.bank` 是「此刻选中的包」，不是「当年学这个词时的包」** —— 用户随时切库（`App.tsx:311-313` 切库即重开一轮），两者无任何因果关系；② 用单值猜多值，**必然把 2323 条错误地塞进一个包**；③ 一旦猜错，用户会在 A 包里看到自己从未在 A 学过的词，**看起来是对的**（这正是 MIGRATION_AUDIT §4.2 警告的「比无归属更糟」）；④ 不可回滚（无法区分哪些是猜的） | ❌ 否决 |
| **③ 复制成 N 份按包分摊** | `generalize` → 5 条，分别挂 5 个候选 ContentId | ① **凭空把用户数据放大 4~5 倍**：错题数、复习队列、统计口径全部虚高；② 把一个「不知道」变成 N 个「假装知道」，**违反证据链要求**；③ 直接引爆配额（2323 条最坏放大 5× = 11615 条新增，按 §2.9 单条 ~304 字符算约 +7 MB）；④ 无法回滚（复制出来的记录与真实记录无法区分） | ❌ 否决 |

**选定 ① 的完整论证（六条）**：

1. **零信息损失**：`{wrongCount, correctStreak, lastWrongAt, nextReviewAt, intervalIdx}` 五个字段**一个不丢**。丢的只是「归属」，而归属**本来就已丢失** —— 方案 ① 是**唯一不新增损失**的方案。
2. **零编造**：方案 ② ③ 都在「制造」归属信息。方案 ① 把「一个知道」显式降级为「明确未知」，符合「审计器不制造假精度」的既定原则（EVIDENCE-INDEX §0 的「不编造」）。
3. **可解释**：用户看到的是「2323 条旧记录无法归属到具体词库，因为旧版本没有记录来源」—— 这是**产品话术能讲清的事实**，而不是「系统抽风了」。
4. **可回滚**：占位键 `legacy:unattributed:<word>` 是**纯派生**的（从旧键一次算出），完整信息（含候选清单）写在 report 里。回滚 = 丢弃新键 + 从备份恢复旧键（§2.7），一句话可说清。
5. **不膨胀**：2323 条**一对一**映射到 2323 条占位记录，条数零增长（只多几个 JSON 字段）。
6. **为未来留门**：候选清单内联在记录里，将来（P2）可以做「让用户逐条认领」——

#### 2.4.2 `analytics` 的 lowercase 键怎么消除

**第一步：迁移时按 ContentId 重建 `words` 表。**

```ts
 *   1. 对每条 analytics word 键 k（lowercase），先在内容侧做两次查找：
```

**第二步：`letters` 表独立**（§1.3）—— 它不进 `gt.learning.v2`，直接搬到 `gt.letterStats.v1`，键名不变。

**第三步：运行时写入口改造**（本轮不实施，属 P1.5 实施阶段，见 §3.6 顺序）：

#### 2.4.4 为什么不做「再归属」的自动尝试

有人会问：既然保留了 `candidates`，为什么不在迁移时就「尽力猜一次」？答案：**迁移脚本没有任何新信息**。它看到的输入与旧记录完全相同（一个裸 word + 当前词表）。任何「猜」都是对同一份输入的重复解释，不产生新证据。**只有在用户重新选择词库、或用户主动认领时，才产生新信息** —— 那是 P2 的交互任务，不是迁移的职责。

### 2.5 `orphan`：**必须不是 N/A** —— 两条路径的设计

**问题的正确定位**：`orphan` 的定义是「旧记录里的 word 在当前 10 包中**完全不存在**」（`migration-audit.mjs:15`）。因此它的**判据天然依赖旧记录**，而旧记录只有两个来源：

| 路径 | 场景 | 数据可达性 | orphan 是否可为 N/A |
|---|---|---|---|
| **A. 浏览器内迁移（真实用户路径）** | 用户在旧版本站点上用的是旧键，打开新版本时在**自己的浏览器里**跑迁移 | **天然有数据** —— 旧键 `gt.review.v1` 就在 `localStorage` 里，脚本 `localStorage.getItem()` 即可读到 | **否。永远可算。** 这是**主路径** |
| **B. CLI 审计（开发者/运维路径）** | 在没有浏览器 profile 的机器上跑脚本 | 必须显式提供 `--user-store=<file>`；不提供则**无源数据** | **允许 N/A，但必须打印明确原因** |

> **`[实测]` 关键事实**：`scripts/migration-audit.mjs:89` 的 `orphanSource` 在不传 `--user-store` 时是 `'N/A（未提供 --user-store，词表本身无法反映历史消失词汇）'` —— 这个 N/A **只属于 CLI 审计路径**。而**浏览器内迁移路径（A）不存在这个限制**：`localStorage` 里就是旧数据，「旧记录」与「词表」在同一个运行时里同时可得，orphan 是**必然能算出的确定值**。

**因此 prompt 里「orphan 不能是 N/A」的正确落地是**：

1. **实现层**：迁移函数 `migrateV1toV2()` 的**唯一入参就是旧存储对象**（`oldStore: LegacyStoreSnapshot`），orphan 由 `oldStore` 与内容真值直接做差集算出（§2.8 伪代码第 3 步）——**函数签名里没有任何「可选快照」的位置**，因此**在实现上不可能退化成 N/A**。
2. **CLI 层**：审计脚本保留「无快照 → N/A」的行为（这是**诚实的**：没数据就不编），但必须**同时打印一行**告诉使用者「浏览器内迁移路径不存在此限制」。
3. **门禁层**（P1.5-RELEASE-GATE 的 G3）：验收判据不是「orphan 是某个数字」，而是「**给定一份旧快照，orphan 必须被算出且与手工核对一致**」，且「**不给快照时，脚本必须显式报 N/A 而不是 0**」（`[实测]` 当前脚本已满足后者）。

**`legacy:orphan:<word>` 的形状**：

```ts
export interface OrphanRecord {
  word: string
  tier: 'orphan'
  /** 为什么判定为 orphan（可枚举，便于聚合统计归因） */
  reason: 'not-in-current-vocabulary'
  review?: LearningReview
  memorize?: LearningMemorize
  analytics?: LearningAnalytics
}
```

**为什么不能丢**：orphan 意味着「用户曾经学过这个词，但它已不在当前 10 包中」。丢弃 = **静默删用户的头**。保留成本近乎为零（不进任何包的选择菜单、不参与排期），但若将来词库重新引入该词，可以直接再归属。

**为什么不能自动删除**：`[实测]` 的合成样本里 `zzz_not_in_content_2026` 与 `useEffect` 都被判为 orphan。**`useEffect` 是 `ts-code` 包声明 case-sensitive 的真实场景**（EVIDENCE-INDEX §11：「真实快照路径已验证：`TreeShaking` → caseConflict、`useEffect` → orphan（已核对 `useEffect`/`Promise` 确实不在 9,346 条里，不是误判）」）。这说明 orphan **不一定等于「垃圾数据」** —— 它可能是「我们的词表还不全」。自动删除等于把「词表不全」这个事实永久抹掉。

### 2.6 幂等性：具体机制

**双条件判定（缺一不可）**：

```ts
/** gt.migration.v1 —— 迁移标记 */
export interface MigrationMarker {
  /** 已完成的最高迁移版本；本设计为 1 */
  version: 1
  /** 迁移开始时间（ISO 8601，本地时区） */
  startedAt: string
  /** 迁移完成时间 */
  finishedAt: string
  /** 源数据指纹：4 个旧键的 (length + 首尾 64 字符) 组合指纹 —— 用于识别「标记在、但源数据已变」 */
  sourceFingerprint: string
  /** 本次迁移产出的记录数，用于与 gt.learning.v2 的实际键数交叉校验 */
  producedCount: number
  /** 回滚令牌（§2.7.2） */
  rollbackToken: string
  /** 迁移器版本，便于将来定位是谁写的 */
  migratorVersion: string   // 如 'learning-migrator/1.0.0'
}
```

**幂等判定逻辑**：

```
on boot:
  marker = read(KEY_MIGRATION)
  if (!marker):
      → 执行迁移（§2.8 的 8 步）
  else if (marker.version < 1):
      → 执行迁移（将来 v2 的升级链）
  else if (marker.version >= CURRENT_VERSION):
      fp = fingerprint(readLegacyKeys())
      if (fp === marker.sourceFingerprint):
          → 已迁移且源数据未变：**零操作直接 return**（不是「重跑一次得到相同结果」，是**根本不跑**）
      else:
          → 源数据在迁移后又被写入（理论上不该发生）：
            记录 warning，**不重跑**（避免覆盖已迁移的新数据），只在 diag 里告警
  else:
      → 版本超前（用户降级了 App）：**不动作**，只告警
```

**为什么用「指纹相等就根本不跑」而不是「重跑一遍得到相同结果」**：后者虽然结果幂等，但每次都付出全量计算成本（`[实测]` 全库 6713 条 JSON.parse + 分档 + 重排序，量级在百毫秒级），且**无法区分「重跑成功」与「重跑其实改了东西」**。「根本不跑」让「已迁移」成为一个**可观测的确定状态**。

**「跑到一半崩溃」的原子性设计**：

```
阶段 1（纯计算，零副作用）：
  读 4 个旧键 → 全部分档 → 构造 next: LearningStoreV2 + report
  ⚠️ 此阶段不写任何 localStorage

阶段 2（单次批量写入）：
  localStorage.setItem(KEY_LEARNING_V2, JSON.stringify(next))
  localStorage.setItem(KEY_LETTER_STATS, ...)
  localStorage.setItem(KEY_TOTALS, ...)
  localStorage.setItem(KEY_CUSTOM_INDEX, ...)
  localStorage.setItem(KEY_BACKUP, JSON.stringify(oldSnapshot))
  ⚠️ 所有业务数据在这一阶段写完

阶段 3（提交点）：
  localStorage.setItem(KEY_MIGRATION, JSON.stringify(marker))
  ⚠️ 这是唯一的「提交」动作。marker 存在 ⇔ 迁移已完成
```

**崩溃恢复的四种情况（穷举）**：

| 崩溃位置 | 磁盘状态 | 下次启动行为 | 正确性 |
|---|---|---|---|
| 阶段 1 中 | 无任何新键 | 重跑（marker 不存在） | ✅ 无副作用 |
| 阶段 2 中 | 部分新键已写、marker 不存在 | 重跑：阶段 1 重算（读的还是**旧键**，未被修改）→ 阶段 2 覆盖写 | ✅ 结果与一次跑完相同 |
| 阶段 3 中（marker 写了一半） | 新键完整、marker 损坏 | 读 marker 失败 → 视为不存在 → 重跑 → 阶段 2 覆盖写相同内容 → marker 重写 | ✅ 幂等 |
| 阶段 3 后 | 新键 + marker 均完整 | 读 marker → 指纹相等 → 零操作 | ✅ |

> **关键设计点：旧键在阶段 1-3 全程只读、绝不修改。** 这是「崩溃后可重跑」的前提。旧键的清理是**独立的第四阶段**（§2.7），且**本轮不实施**。

### 2.7 可回滚

#### 2.7.1 旧键是否删除

**结论：不删除。四个旧键在迁移后原样保留。**

理由（三条）：

1. **回滚是零成本的一句话**：回滚 = `删 gt.learning.v2 等 5 个新键 + 删 gt.migration.v1`。旧键从未被碰过，**因此回滚不需要恢复数据、不需要解析备份** —— 这是最强形态的可回滚。
2. **体积代价可忽略且已实测**：`[实测]` 4 个旧键合计 2.773 MiB（含 `gt.customBanks.v1` 的话更多，但它含用户内容、本就不该删）。迁移后新键 3.894 MiB。**两者并存 = 6.667 MiB，占真实配额（10 MiB）的 66.7%、占保守 5 MiB 口径的 127%** —— 见下。
   > ⚠️ **这里必须停下来指出一个真实风险**：若按保守的 5 MiB 口径，「双份并存」**会超配额**。因此**不能无条件双份并存**。修正方案：**迁移时把 `gt.learning.v2.backup` 作为第二副本的替代** —— 即**备份里放的正是旧键的完整快照**，有了备份就不必再保留旧键的**内容**（旧键可以只保留一个空的占位 + 备份键里的完整数据）。
   > **最终方案（三选一，按可用配额自适应）**：
   > - **默认（配额充足，真实 10 MiB 环境）**：4 个旧键原样保留 + 备份键。回滚一句话。
   > - **配额紧张（`navigator.storage.estimate()` 显示 >70% 已用）**：旧键内容清空（保留键名 + 写一个 `{"__migrated__":true}` 占位），完整快照只在 `gt.learning.v2.backup`。回滚 = 从备份恢复 + 删新键。仍是两句话。
   > - **配额红线（>90%）**：不写备份键，先删旧键再迁（有损回滚：只能靠用户重新登录/清库）。**这种情况必须先在 UI 上显式征求用户同意**。
3. **旧键的最终清理时机**：**至少保留到 P1.5 之后的第 2 个 release 周期**（建议 1 个月或 3 个版本），届时用户基数已实测稳定、新键无异常增长，再单独提一次「清理旧键」的小改动。**本轮不做。**

#### 2.7.2 `rollbackToken` 设计

```ts
/**
 * 回滚令牌：一次迁移的唯一标识 + 回滚所需全部信息。
 * 存在两处：① gt.migration.v1.rollbackToken（当前值）
 *          ② gt.learning.v2.__meta__（记录态副本，防 marker 被外部清掉）
 */
export interface RollbackToken {
  /** 随机 + 时间戳，唯一标识本次迁移（形如 'mig-1759000000000-7f3a2c'） */
  id: string
  /** 备份键名，回滚时从这里读 */
  backupKey: 'gt.learning.v2.backup'
  /** 迁移时被写入的全部新键（回滚时逐个删除） */
  writtenKeys: string[]
  /** 备份键里保存的旧键名单（回滚时逐个恢复） */
  backedUpKeys: LegacyKey[]
  /** 旧键在本机是否保留了完整内容（true=保留，false=已清空为占位） */
  legacyKeysRetained: boolean
}
```

**回滚操作（一句话版）**：`rollbackLearningV1(token)` —— 删除 `token.writtenKeys` 全部键 → 从 `token.backupKey` 恢复 `token.backedUpKeys` → 删除 `gt.migration.v1`。

#### 2.8.2 伪代码：`migrateV1toV2(oldStore): { next, report }`

```ts
/* =====================================================================
 * migrateV1toV2 —— 纯函数（**零 localStorage 副作用**，便于单测与 dry-run）
 *
 * 为什么必须是纯函数：
 *   ① dry-run 与真实迁移必须走同一段代码 —— 否则「dry-run 通过、真实迁移出错」
 *      这一类事故无法避免。dry-run 只是「算出 next 和 report，然后不落盘」。
 *   ② 单测可以直接喂构造的 oldStore，不需要 mock localStorage。
 * ===================================================================== */

export interface LegacyStoreSnapshot {
  review:      Record<string, ReviewEntry>         // gt.review.v1
  memorize:    Record<string, MemRecord>           // gt.memorize.v1
  analytics:   Analytics                           // gt.analytics.v1（含 letters + 4 标量）
  customBanks: CustomBank[]                        // gt.customBanks.v1
  /* 注意：gt.streak.v1 不在入参里 —— 它不参与迁移（§2.1） */
}

export interface ContentTruth {
  /** Map<原词形, 包名[]> —— 来自 migration-audit.mjs:61-67 的同构结构 */
  wordToPkgs: Map<string, string[]>
  /** Map<lowercase, Set<原词形>> —— 用于 analytics 的 lowercase 回推（:70-77 + learning-consistency loadContent） */
  lowerToForms: Map<string, Set<string>>
  /** Map<包名, { namespace: string; contentVersion: number; contentChecksum: string }> */
  pkgInfo: Map<string, { namespace: string; contentVersion: number; contentChecksum: string }>
}

export interface MigrateResult {
  next: {
    learning: LearningStoreV2
    letterStats: LetterStats
    totals: GlobalTotals
    customBankIndex: CustomBankIndex
    backup: LegacyStoreSnapshot
  }
  report: MigrationReport
}

const CURRENT_VERSION = 1
const MIGRATOR_VERSION = 'learning-migrator/1.0.0'

export function migrateV1toV2(
  oldStore: LegacyStoreSnapshot,
  truth: ContentTruth,
  opts: { now: number; runtime: 'browser' | 'cli'; canReadQuota?: boolean } = { now: Date.now(), runtime: 'browser' },
): MigrateResult {
  const startedAt = new Date(opts.now).toISOString()
  const warnings: MigrationWarning[] = []
  const learning: LearningStoreV2 = {}
  const ambiguousSample: { word: string; candidates: string[] }[] = []

  /* ---- 步骤 1：收集「全部出现过的 word」——三源并集，**原词形逐字符** ---- */
  // ① review / memorize 的键是原词形（保留大小写）
  // ② analytics.words 的键是 lowercase，**需要回推**，故先用 lowercase 集合收集
  const wordsFromExact = new Set<string>([
    ...Object.keys(oldStore.review ?? {}),
    ...Object.keys(oldStore.memorize ?? {}),
  ])
  const wordsFromLower = new Set<string>(Object.keys(oldStore.analytics?.words ?? {}))

  /* ---- 步骤 2：analytics lowercase 键 → 原词形回推（§2.4.2） ---- */
  const invalidWords: string[] = []
  const lowerHitWords: string[] = []
  /** Map<原词形, {analytic?: WordStat}> —— 回推后的 analytics 分片 */
  const analyticsByWord = new Map<string, WordStat>()
  for (const lk of wordsFromLower) {
    if (!isValidWordKey(lk)) { invalidWords.push(lk); continue }
    const forms = truth.lowerToForms.get(lk)
    if (!forms) {
      // lowercase 也在内容侧不存在 → 这个键本身就是个 orphan（保留原样，进 orphan 档）
      analyticsByWord.set(lk, oldStore.analytics.words[lk])
      continue
    }
    if (forms.size > 1) {
      // [实测] 真实语料不可达（contentCaseCollisions = 0）；一旦命中，**不猜**，标记冲突
      warnings.push({ code: 'CASE_CONFLICT', message: '同一 lowercase 对应多种原词形，无法回推', words: [...forms] })
      continue
    }
    const form = [...forms][0]
    if (form !== lk) lowerHitWords.push(lk)          // 该键确实被 lowercase 过
    analyticsByWord.set(form, oldStore.analytics.words[lk])
  }
  if (lowerHitWords.length) {
    warnings.push({
      code: 'ANALYTICS_LOWERCASE_HIT',
      message: `analytics.words 有 ${lowerHitWords.length} 个 lowercase 键被回推为原词形`,
      words: lowerHitWords.slice(0, 100),
    })
  }
  if (invalidWords.length) {
    warnings.push({ code: 'INVALID_KEY_DROPPED', message: '非法键已丢弃（不迁移、不计数）', words: invalidWords })
  }

  /* ---- 步骤 3：三档分档 + 归属（§2.3 / §2.4 / §2.5） ---- */
  const allWords = new Set<string>([...wordsFromExact, ...analyticsByWord.keys()])
  const orphanWords: string[] = []
  const tiers = { resolved: 0, ambiguous: 0, orphan: 0, caseConflict: 0, invalid: 0 }

  for (const word of allWords) {
    if (!isValidWordKey(word)) { tiers.invalid++; continue }
    const pkgs = truth.wordToPkgs.get(word)
    const lowerKnown = truth.lowerToForms.has(word.toLowerCase())

    // 三源分片（缺哪个就没有哪个字段）
    const review    = oldStore.review?.[word]
    const memorize  = oldStore.memorize?.[word]
    const analytic  = analyticsByWord.get(word)

    if (!pkgs && !lowerKnown) {
      /* --- ORPHAN：与 10 包完全无交集（**绝不为 N/A**） --- */
      learning[`legacy:orphan:${word}`] = { word, tier: 'orphan', reason: 'not-in-current-vocabulary',
        ...(review ? { review } : {}), ...(memorize ? { memorize } : {}), ...(analytic ? { analytics: analytic } : {}) }
      orphanWords.push(word); tiers.orphan++
      continue
    }

    if (!pkgs && lowerKnown) {
      /* --- CASE CONFLICT：小写能命中但精确不能（真实语料实测 0 条） --- */
      // 保守处理：不猜归属，降级到 orphan 档并显式告警（宁可不迁，不可迁错）
      learning[`legacy:orphan:${word}`] = { word, tier: 'orphan', reason: 'not-in-current-vocabulary',
        ...(review ? { review } : {}), ...(memorize ? { memorize } : {}), ...(analytic ? { analytics: analytic } : {}) }
      orphanWords.push(word); tiers.caseConflict++
      warnings.push({ code: 'CASE_CONFLICT', message: `精确不命中但小写命中：${word}`, words: [word] })
      continue
    }

    if (pkgs!.length >= 2) {
      /* --- AMBIGUOUS：跨 ≥2 包，无法反推（§2.4） --- */
      const candidates = pkgs!.slice().sort()
        .map((p) => `content:word:${truth.pkgInfo.get(p)!.namespace}:${word}`)
      learning[`legacy:unattributed:${word}`] = { word, tier: 'ambiguous', candidates,
        ...(review ? { review } : {}), ...(memorize ? { memorize } : {}), ...(analytic ? { analytics: analytic } : {}) }
      tiers.ambiguous++
      if (ambiguousSample.length < 20) ambiguousSample.push({ word, candidates })
      continue
    }

    /* --- RESOLVED：唯一映射（4390 条的主体） --- */
    const pkg = pkgs![0]
    const info = truth.pkgInfo.get(pkg)!
    const contentId = `content:word:${info.namespace}:${word}`
    const rec: LearningRecord = { contentId, contentVersion: info.contentVersion,
      contentChecksum: info.contentChecksum, freshness: 'ok',
      ...(review ? { review } : {}), ...(memorize ? { memorize } : {}), ...(analytic ? { analytics: analytic } : {}) }
    // 幂等冲突：键已存在（理论上不会，因为入参是旧键）→ 取时间戳更「新」者（MIGRATION_AUDIT §4.1）
    if (learning[contentId]) {
      warnings.push({ code: 'DUPLICATE_SOURCE_MERGE', message: '目标键已存在，取较新者',
        word, sources: ['review|memorize|analytics'] })
    }
    learning[contentId] = rec
    tiers.resolved++
  }

  /* ---- 步骤 4：letters + 全局标量独立搬走（§1.3） ---- */
  const letterStats: LetterStats = { letters: { ...(oldStore.analytics?.letters ?? {}) } }
  const totals: GlobalTotals = {
    totalKeys:    oldStore.analytics?.totalKeys    ?? 0,
    totalCorrect: oldStore.analytics?.totalCorrect ?? 0,
    totalWords:   oldStore.analytics?.totalWords   ?? 0,
    bestWpm:      oldStore.analytics?.bestWpm      ?? 0,
  }

  /* ---- 步骤 5：自建库索引（§2.1.1，只建索引不迁学习记录） ---- */
  const customBankIndex: CustomBankIndex = {}
  for (const b of oldStore.customBanks ?? []) {
    customBankIndex[b.id] = {
      bankId: b.id,
      namespace: `custom-${b.id.replace(/^custom-/, '')}`,
      words: b.words.map((w) => w.word),      // 原词形，保留大小写
      createdAt: b.createdAt,
    }
  }

  /* ---- 步骤 6：备份 = 旧键原样快照（§2.7） ---- */
  const backup: LegacyStoreSnapshot = JSON.parse(JSON.stringify(oldStore))

  /* ---- 步骤 7：体积核算（供 quota 判定与 report 使用） ---- */
  const learningJson = JSON.stringify(learning)
  const bytesUtf16 = learningJson.length * 2
  const quotaPercent: number | null = opts.canReadQuota ? null : null   // 真实值由调用方从 navigator.storage 注入

  /* ---- 步骤 8：组装 report ---- */
  const report: MigrationReport = {
    reportVersion: 1, migratorVersion: MIGRATOR_VERSION, runtime: opts.runtime,
    startedAt,
    finishedAt: new Date(opts.now + 1).toISOString(),   // 真实实现用 Date.now() 收尾
    durationMs: 1,
    sourceKeys: [
      { key: 'gt.review.v1',     present: !!oldStore.review,      entryCount: Object.keys(oldStore.review ?? {}).length,     bytesUtf16: (localStorageSafeJson(oldStore.review) ?? '{}').length * 2,     inScope: true },
      { key: 'gt.memorize.v1',   present: !!oldStore.memorize,    entryCount: Object.keys(oldStore.memorize ?? {}).length,   bytesUtf16: (localStorageSafeJson(oldStore.memorize) ?? '{}').length * 2,   inScope: true },
      { key: 'gt.analytics.v1',  present: !!oldStore.analytics,   entryCount: wordsFromLower.size,                            bytesUtf16: (localStorageSafeJson(oldStore.analytics) ?? '{}').length * 2,  inScope: true },
      { key: 'gt.customBanks.v1',present: !!oldStore.customBanks, entryCount: (oldStore.customBanks ?? []).length,            bytesUtf16: (localStorageSafeJson(oldStore.customBanks) ?? '[]').length * 2,inScope: true },
      { key: 'gt.streak.v1',     present: false, entryCount: 0, bytesUtf16: 0, inScope: false,
        reason: 'keys are dates, no word dimension' },
    ],
    targetKeys: [
      { key: 'gt.learning.v2',        entryCount: Object.keys(learning).length, bytesUtf16, quotaPercent },
      { key: 'gt.letterStats.v1',     entryCount: 1, bytesUtf16: JSON.stringify(letterStats).length * 2, quotaPercent: null },
      { key: 'gt.totals.v1',          entryCount: 1, bytesUtf16: JSON.stringify(totals).length * 2,     quotaPercent: null },
      { key: 'gt.customBankIndex.v1', entryCount: Object.keys(customBankIndex).length, bytesUtf16: JSON.stringify(customBankIndex).length * 2, quotaPercent: null },
      { key: 'gt.learning.v2.backup', entryCount: 4, bytesUtf16: JSON.stringify(backup).length * 2,     quotaPercent: null },
    ],
    tiers, orphanWords: orphanWords.slice(0, 100), ambiguousSample, warnings,
    rollbackToken: {
      id: `mig-${opts.now}-${Math.random().toString(36).slice(2, 8)}`,
      backupKey: 'gt.learning.v2.backup',
      writtenKeys: ['gt.learning.v2', 'gt.letterStats.v1', 'gt.totals.v1', 'gt.customBankIndex.v1', 'gt.learning.v2.backup'],
      backedUpKeys: ['gt.review.v1', 'gt.memorize.v1', 'gt.analytics.v1', 'gt.customBanks.v1'],
      legacyKeysRetained: true,
    },
    outcome: warnings.some((w) => w.code === 'CASE_CONFLICT' || w.code === 'INVALID_KEY_DROPPED') ? 'degraded' : 'ok',
    orphanUnavailableReason: null,     // 浏览器内路径永远为 null（§2.5）
  }

  return { next: { learning, letterStats, totals, customBankIndex, backup }, report }
}

/* ---- 落盘层（**有副作用**，与上面的纯函数分离） ---- */
export function applyMigration(result: MigrateResult, marker: MigrationMarker): void {
  // 阶段 2：批量写业务数据（顺序无要求，但必须全部在 marker 之前）

  localStorage.setItem('gt.letterStats.v1',     JSON.stringify(result.next.letterStats))

}
```

## 3. (c) 统一 `PersistentStore` 设计

### 3.1 目标目录与文件划分

```
src/lib/persistence/
  storage.ts       —— 底层读写原语（唯一接触 localStorage 的地方）
  quota.ts         —— QuotaExceeded 检测 + 熔断策略 + 容量观测
  serializer.ts    —— Codec<T> 接口 + 通用 JSON 编解码 + 校验钩子
  migration.ts     —— 迁移注册表 + 幂等执行器（§2 的落盘层）
  diagnostics.ts   —— 静默失败的统一上报（console + ring buffer + 可选 gt.diag.v1）
```

**为什么必须是 5 个文件（而不是 1 个）**：`storage.ts` 是**唯一允许触碰 `localStorage` 全局对象的文件**。任何其它文件（包括 `persistence/` 内的其它三个）都必须通过它 —— 这是把「测试替身 / 未来换 IndexedDB」的可能性收敛到一个点。`quota.ts` 必须独立是因为它是**策略**（清哪些、清多少），而 `storage.ts` 只提供**能力**（写、失败、报错类型）。

### 3.2 `storage.ts` —— 导出签名

```ts
/** 存储写入结果：**取代现有 4 处静默 catch 与 1 处 console.warn** */
export interface SaveResult {
```

### 3.3 `serializer.ts` —— `Codec<T>` 接口

```ts
/**
 * 编码器：把「领域对象」与「localStorage 里的一串字符」互相转换。
 *
 * 为什么需要它：现状 5 个 store 各自 `JSON.parse` / `JSON.stringify`，
 * 且只有 reviewStore 做了形状校验（reviewStore.ts:36 的
 * `typeof parsed === 'object' && !Array.isArray(parsed)`），其余 4 个
 * **直接把 parse 结果 cast 成目标类型**（memorizeStore.ts:22、streak.ts:28、
 * customBanks.ts:15、analytics.ts:39 的 `{ ...EMPTY, ...parsed }` 更危险：
 * 一个数组 spread 进去会得到数字键的怪对象）。
 */
export interface Codec<T> {
  /** 领域对象 → 字符串 */
  encode(value: T): string
  /** 字符串 → 领域对象；**必须自己做形状校验**，不合法返回 null（不抛） */
  decode(raw: string): T | null
  /** 独立的合法性谓词（供写入前自检与读取后诊断复用） */
  validate(value: unknown): value is T
  /** 空值（键不存在时的默认值）—— 必须是**新对象**，不能共享引用 */
  empty(): T
}

/** 简单 Record<string, V> 表的通用 codec 工厂（覆盖 4 个 store 的主形状） */
export function mapCodec<V>(
  validateEntry: (v: unknown) => v is V,
): Codec<Record<string, V>>

/** 数组 codec（gt.customBanks.v1 用） */
export function arrayCodec<T>(validateItem: (v: unknown) => v is T): Codec<T[]>

/** 由 Codec<T> + 键名组成一个带类型的存储句柄 */
export interface TypedStore<T> {
  key: string
  load(): T
  save(value: T): SaveResult
  /** 读原始值 + 解码结果，供诊断使用 */
  inspect(): { raw: string | null; decoded: T | null; valid: boolean }
}
export function typedStore<T>(key: string, codec: Codec<T>, quota?: QuotaPolicy<T>): TypedStore<T>
```

**校验钩子的具体实现要求**（这是 §3.4 问题 3 的答案）：

| store | 现状校验 | 统一后 `validateEntry` 必须检查 |
|---|---|---|
| `gt.review.v1` | `typeof === 'object' && !Array.isArray` | 上述 + 5 个字段均为 `number`（`intervalIdx` 额外要求 `0 <= x < INTERVALS_DAYS.length`） |
| `gt.memorize.v1` | **无** | `status` ∈ `{known,fuzzy,unknown}`、`reviews`/`lastAt` 为 `number` |
| `gt.analytics.v1` | **无**（且 spread 合并有隐患） | `letters` 是对象、`words` 是对象、4 个标量为有限 `number` |
| `gt.streak.v1` | **无** | 键匹配 `/^\d{4}-\d{2}-\d{2}$/`、`words`/`seconds` 为 `number` |
| `gt.customBanks.v1` | **无**（`as CustomBank[]`） | 是数组、每项有 `string id` / `string name` / `Array words` / `number createdAt` |

> **一条硬约束**：`decode` 遇到**单条**非法项时，应丢弃该条并**继续**（返回合法子集），而不是整表判废。理由：`[实测]` 的合成数据里存在注入的非法键（空串 / `'   '` / 超长），真实用户的库里同样可能有历史脏数据。整表判废 = **因为一条脏数据丢掉整本错题本**，这是最坏的用户体验。丢弃的条目必须进 diag（§3.5）。

### 3.4 四个现存问题的逐个方案

#### 问题 1：静默 `catch {}` —— 统一后怎么报错

`[读码]` 现状盘点（我逐个核对过行号）：

| 文件:行 | 现状 | 严重度 |
|---|---|---|
| `analytics.ts:48` | `catch { /* 忽略 */ }` | 中（节流写，丢了下次会写） |
| `memorizeStore.ts:37` | `catch { /* 隐私模式下忽略 */ }` | **高**（每条作答都写，丢了就是丢学习记录） |
| `streak.ts:38` | `catch { /* 忽略隐私模式写入失败 */ }` | 中 |
| `customBanks.ts:22` | **无 catch**（会抛到调用方 → 可能炸 React 渲染） | **最高** |
| `App.tsx:81` `writeStorage` | `catch { /* 隐私模式下忽略 */ }` | 中（7 个设置键共用） |
| `speech.ts:34` / `i18n/index.tsx:50` | `catch { /* 隐私模式下忽略 */ }` | 低（单标量，丢了只是偏好回默认） |

**方案：三件式，不是二选一**：

```ts
/** ① 同步返回值：调用方需要立刻决策时用（reviewStore 已有此模式，推广开） */
export interface SaveResult { ok: boolean; evicted: number; reason: ...; error?: unknown }

/** ② 全局订阅：调用方不关心单次结果、但 UI 需要「有个地方能说」时用 */
export type SaveFailureEvent = { key: string; result: SaveResult; at: number }
export function onSaveFailure(cb: (e: SaveFailureEvent) => void): () => void   // 返回退订函数

/** ③ diag 落盘：跨会话可查（§3.5） */
export function reportDiag(entry: DiagEntry): void
```

**为什么不做「回调参数」**（排除一个候选）：回调需要每个调用点都传，而 `[读码]` 的调用点分散在 6 个文件 11 处（`App.tsx` × 5、`Memorize.tsx` × 4、`ReviewPanel.tsx` × 1、`BankManager.tsx` × 1、`StatsPanel.tsx` × 1）。要求每处都传 = **必然有人忘**。改为「`save()` 返回 `SaveResult` + `persistence` 层**无条件**触发 `onSaveFailure` 事件」，把「必须记得处理」变成「默认就上报」。

**为什么不做「抛异常」**：`[实测]` `analytics.ts:47` 的写入发生在 React 状态更新链路上（`App.tsx:331` 的 800ms 节流 effect），抛出会穿透到 React 渲染 → 触发 ErrorBoundary（`AppErrorBoundary.tsx` 存在）→ **整个页面白屏因为一次 localStorage 写失败**，这是不可接受的。

**UI 层建议**：`onSaveFailure` 的订阅者只做一件低成本的事 —— 在 `App.tsx` 里把最近一次失败塞进一个 `useState`，渲染一个**不阻断操作**的顶部细条提示「学习记录暂时无法保存（浏览器存储受限）」，并在下次成功写入后自动消失。

#### 问题 2：Quota 熔断只有 `reviewStore` 有 —— 统一策略

**先摆事实（防止过度设计）**：`[实测]`（引自 EVIDENCE-INDEX §10.2，我本轮未重跑压测，标注为引用）S7 满配（review 全库 + memorize 全库 + analytics + streak 365 天）= **2,953,556 B**，占真实配额 **28.19%**，**撞不到 Quota**。`[实测]` 我本轮新算的迁移后 `gt.learning.v2` = 3.894 MiB = **38.97%**。两者相加（迁移后 + streak）= 约 **41%**。**结论：Quota 不是当前瓶颈，统一策略不应把熔断逻辑复制到每个 store。**

**因此统一策略是「能力统一、策略可选、观测必到」**：

```ts
/** 熔断策略：**只有需要它的 store 才配置**（当前只有 gt.learning.v2 与旧的 gt.review.v1） */
export interface QuotaPolicy<T> {
  /** QuotaExceeded 时，从 value 里挑出「可以丢」的条目 —— 返回新的 value + 丢了几个 */
  evict(value: T): { next: T; evicted: number }
  /** 最多几轮（reviewStore.ts:52 的 QUOTA_ROUNDS = 3） */
  rounds: number
  /** 本轮刚写入、**绝不能丢**的条目（reviewStore.ts:66 的 protectedKey） */
  protectedKey?: string
}

export function withQuota<T>(store: TypedStore<T>, policy: QuotaPolicy<T>): TypedStore<T>
```

**四个 store 的策略分配（明确结论）**：

| store | 是否配 QuotaPolicy | 理由 |
|---|---|---|
| `gt.learning.v2` | ✅ 配（继承 `gt.review.v1` 的「按 `intervalIdx` 降序清、每轮 1/4、保护本轮词」） | 唯一有真实增长压力的键（§2.9 实测 3.894 MiB） |
| `gt.letterStats.v1` | ❌ 不配（固定 26 键） | 体积恒定（`[实测]` 1,354 B），永远不会是压垮配额的那根稻草 |
| `gt.totals.v1` | ❌ 不配（固定 4 标量） | 同上 |
| `gt.streak.v1` | ❌ 不配，但**加老化**（见下） | `[实测]` 365 天 = 602 B；但理论上无限增长，加一个「只保留最近 400 天」的裁剪（与 `getStreakDays` 的 400 天窗口 `streak.ts:71` 一致） |
| `gt.customBanks.v1` | ❌ 不配 | **用户自己导入的内容，丢了不可接受**；撞 Quota 时应当**明确失败并告知用户**（`SaveResult.ok=false` + UI 提示「存储空间不足，请先删除部分自建词库」），而不是替他决定丢哪个 |

**「观测必到」的具体落地**（这是 prompt 里「必须可观测」的答案）：

```ts
/** 容量观测：写入前估算，写入后记录。不引入后端，纯前端 */
export interface QuotaSnapshot {
  at: number
  /** 本应用占用的 UTF-16 字节（persistence.totalAppBytes()） */
  appBytes: number
  /** navigator.storage.estimate() 的 quota（可能为 null —— [实测] headless 下返回 null，EVIDENCE-INDEX §4.1） */
  browserQuota: number | null
  /** 已知口径下的估算占比：真实 10 MiB（EVIDENCE-INDEX §10.1 实测）或保守 5 MiB */
  estimatedPercentOf10MiB: number
  estimatedPercentOf5MiB: number
  /** 每个应用键的字节数，降序 */
  perKeyBytes: { key: string; bytes: number }[]
}

/** 在写入前调用一次（开销：读 n 个键的 length 求和，n 很小，<1ms） */
export function snapshotQuota(): QuotaSnapshot

/** 超过阈值时通过 diag 上报 + 通过 onSaveFailure 之外的另一条事件通道通知 UI */
export const QUOTA_WARN_PERCENT = 70
export type QuotaPressureEvent = { snapshot: QuotaSnapshot; percent: number }
export function onQuotaPressure(cb: (e: QuotaPressureEvent) => void): () => void
```

**为什么 `snapshotQuota` 用「读 length 求和」而不是 `navigator.storage.estimate()`**：`[实测]` 后者在本机 headless Chrome 下返回 `{quota: null, usage: null}`（EVIDENCE-INDEX §4.1），**不可依赖**。而 `localStorage` 的 `key`/`getItem` 是**同步的、必定可用的** —— 用「所有 gt.* 键的 `value.length * 2` 求和」得到的是**确定值**。`estimate()` 若可用则作为**附加**信息（`browserQuota` 字段允许为 null）。

#### 问题 4：`diagnostics` —— 那 5 个静默 catch 到底要不要上报

**结论：要上报，但只上报 3 类，且落地形态是「console + 内存 ring buffer + 可选 `gt.diag.v1`」——不引入任何后端。**

**先回答「要不要」**：5 个静默 catch 中有 **2 个必须上报**：

1. `memorizeStore.ts:37` —— 每次作答都写，静默失败 = 用户学了 100 个词而系统只记住 60 个，**用户完全无感**。这是**必须让人知道**的。
2. `customBanks.ts:22` —— 会抛异常（不是静默），可能导致渲染中断。

其余 3 个（`analytics` / `streak` / 设置键）**丢失后果可恢复**（下次写入会重试、或丢失的只是展示统计），但也应当进 ring buffer 以便排查。

**三件套设计**：

```ts
/** diag 条目：**结构化、可枚举 code、不含用户词形明文** */
export interface DiagEntry {
  /** 单调递增序号（ring buffer 定位用） */
  seq: number
  at: number
  /** 可枚举的 code（禁止自由文本 —— 否则无法聚合） */
  code:
    | 'STORAGE_WRITE_FAILED'
    | 'STORAGE_READ_CORRUPT'
    | 'STORAGE_ENTRY_DROPPED'       // decode 时丢了单条脏数据
    | 'QUOTA_EVICTED'
    | 'QUOTA_PRESSURE'
    | 'MIGRATION_WARNING'
    | 'MIGRATION_ABORTED'
  /** 涉及的存储键（不是用户数据，是键名，安全） */
  key: string
  /** 计数类信息（丢了几个、占多少百分比） */
  count?: number
  percent?: number
  /** 原始错误的 name（如 'QuotaExceededError'），**不存 message、不存 stack** */
  errorName?: string
}

/** 内存 ring buffer：**默认容量 100**，不落盘（零成本、零隐私风险） */

export function reportDiag(entry: Omit<DiagEntry, 'seq' | 'at'>): void
export function clearDiagBuffer(): void

/**
 * 可选落盘：仅当用户**显式开启**（设置页默认关闭）时写 'gt.diag.v1'。

 *  ① 隐私 —— 键名里不含词，但「用户在什么时间频繁写失败」本身就是行为数据；
 *  ② 体积 —— diag 落盘会与 Learning 争配额，而配额正是 diag 要观测的对象，
 *     这构成循环依赖（观测者与被观测者抢同一份资源）。
 * 若开启：容量固定 50 条，超出 FIFO 淘汰，且**任何写入失败时静默丢弃**（不可能自我诊断）。
 */
export const KEY_DIAG = 'gt.diag.v1'
export function setDiagPersistence(enabled: boolean): void
```

**为什么不做「上报到后端」**：项目**零后端**（`EVIDENCE-INDEX §1` 明确 `.env.example` 说明「本项目运行时零环境变量依赖」；`streak.ts:2-3` 的注释也写「纯前端零后端」）。引入上报端点会改变项目的部署性质（需要 CORS、需要隐私政策、需要合规审查），**远超 P1.5 范围**。若将来要做，正确的顺序是先做 `gt.diag.v1` 落盘 → 用户可主动导出/上报 → 再做自动上报。

**「用户可见的诊断入口」**：建议在设置页放一个「导出诊断信息」按钮（读 `getDiagBuffer()` + `snapshotQuota()` → 下载 JSON）。这样 diag 的**消费方式**是「用户遇到问题时主动导出给我们」——这是**零后端**前提下唯一诚实的方案，且与 `EVIDENCE-INDEX §3.3` 已有的「让用户导出 localStorage 快照」流程天然衔接。

### 3.5 迁移路径：5 个 store 改走 `PersistentStore` 的实施顺序

1. **`analytics` 拆分 + `reviewStore` 迁移 + 迁移执行器**：因为 `gt.learning.v2[id].analytics` 的数据来自 `analytics.words` 的重建，而 `review`/`memorize` 来自另外两个键。**三者合并到同一张表**这个动作本身是原子的 —— 分开上会出现「一半记录在新表、一半在旧表」的中间态，任何读代码都会得到错的数据。
2. **`M` 与读侧切换**：迁移写 `gt.learning.v2` 之后，`App.tsx` / `Memorize.tsx` / `ReviewPanel.tsx` 的**读**必须同时切到新键。若只迁移不切读，页面读旧键会看到「全部数据消失」。
3. **`M` 与 `gt.bank` 的语义变更**（§3.6）：迁移后「当前词库」不再是歧义的来源，但 UI 上「按包筛选」需要新逻辑。

### 3.6 一个必须同时决定的连带项：`gt.bank` 的语义

**问题**：`gt.bank`（`App.tsx:91`）存的是「用户当前选中的词库裸 id」（如 `'ai-core'`）。迁移后，Learning 记录的主键是 ContentId，**「用户在哪个包里学的」这件事由 ContentId 自身携带**。因此 `gt.bank` 从「学习归属的唯一线索」退化为「UI 的当前筛选器」。

**这带来两个必须处理的点**：

1. **`App.tsx:252` `reviewSingleWord(word)` 必须改造**：它现在用 `bankWords.find(w => w.word.toLowerCase() === word.toLowerCase())` 找词。迁移后必须改为「从 ContentId 解析出 `localId` 与 `namespace` → `getContent(contentId)`」（`registry.ts:123` 已提供且口径正确，见 §9.1 的修复）。
2. **`gt.bank` 保持不动**（它是个 UI 偏好，不是 Learning 数据）。但是 **`[读码]` 注意**：`App.tsx:151-153` 有一个 `useEffect(() => { setCustomBanks(loadCustomBanks()) }, [bankId])`，即**每次切库都重读自建库**。迁移后 `gt.customBankIndex.v1` 的读取也要挂进同一个 effect，否则自建库的学习记录会有 1 个 tick 的可见延迟。
