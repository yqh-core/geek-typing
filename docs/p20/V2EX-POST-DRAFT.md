**分享一个自己做的开源项目，以及被逼出来的几个技术取舍。**

做的是一个英语打字学习站（`https://geek-typing.pages.dev`），主线是「用打字记单词」：
屏幕上给一个词，你敲出来，拼错就重来。本地优先，不用注册，离线可用。

但这篇我想聊的不是产品，是**内容管线**——词库那部分花的力气比业务代码多。

### 一、词库为什么是 JSON 而不是 SQLite

先说结论：**因为词库是内容，不是用户数据。**

最初想过 SQLite，理由很直接：9438 条词条带查询需求（按 tag 筛、按包加载），
JSON 文件每次筛选都得全量 parse。真正让我放弃的是另一个理由：

词库要过**许可入库硬门**。每个包必须登记来源、SPDX 协议、内容 SHA-256，
许可判定不通过直接 CI 判红。用 SQLite 就得额外维护 schema 迁移 + 二进制文件，
而 JSON 天然是**可以逐字节 diff 的**——许可门直接对文件算 SHA-256，
人也能用 git diff 看出这次改了哪几个词。

代价是查询性能，我接受了这个代价：13 个包总共 1.4 MB，
最大的单包（3000 词）也不到 500 KB，浏览器 parse 是个位数量级。
**为了一次不存在的性能问题引入二进制存储，是不划算的。**

### 二、离线优先，以及为什么 `inline` 和 `lazy` 要分开

PWA 要离线能用，词库就得能整包带走。这里做了个区分：

- `go-code` / `ts-code` / `ai-core` 这几个包标 `offline.policy: "inline"`（内联进主包）
- 考试大包标 `"lazy"`（首次进入时按需拉取并缓存）

判断依据是**体积收益**。三个小包加起来 14 KB，内联的边际成本几乎为零，
换来的是「用户第一次打开就有内容，不用等网络」。3000 词的大包内联进来会让主包
多 500 KB，对首屏是实打实的伤害，所以走 lazy。

### 三、体积棘轮：这是我被坑得最久的一处

主包体积不能涨。但「不能涨」这种规则有个致命问题：**它挡不住「改小一次、
之后慢慢涨回来」**。真正难受的是**扩词**场景：加词条必然涨体积，
但扩词库是核心功能，不能禁。

所以做了一条**棘轮**（ratchet）：基线落盘进仓库，只有变小才允许更新基线，
而且**重记基线时如果发现清单变长，直接抛致命错误**。

> 源码里的硬约束原文：
> 「清单**变长**时一律拒绝借记基线 —— 否则棘轮可以被「重记一次」顶破，
> 这是扩词膨胀的入口」

这里的取舍是：**牺牲一点灵活性，换「规则不可能被绕过」。**
另外还加了道预热清单的绝对上限——扩词时代预热只许减不许增，
因为扩词会让预热天然变慢，与其等性能掉下来才发现，不如先卡死。

这套东西的通用价值在于：**任何"限制类"门禁，都必须有"只许变严不许变松"的棘轮，
否则约束会被一次合法操作顶破。**

### 四、内容包为什么必须带 checksum

每个包的 `manifest.json` 里都有 `contentChecksum`（SHA-256），
门禁会校验「source checksum == 载荷实体 SHA-256」。

起因是一个真实问题：词条是 JSON 文本，最容易发生的是**有人手改了一个词、
但没走构建流程**，导致 manifest 描述的和磁盘上的不一致。
当时是构建产物能过、实际内容已经漂了。

有了 checksum + 门禁校验，任何绕过流程的手改都会当场判红。
**这比 review 可靠——review 会漏，校验不会。**

### 五、许可这一块踩的坑（可能对做内容站的人有用）

我给每个包都登记了来源和 SPDX，判定走一张矩阵。
当时一个包标了 `license.commercialUse: true`，门禁判绿，我就以为没问题了。

后来意识到不对：**`commercialUse`（能不能商用）不等于「能不能再分发」**。
我写的门禁只校验了前者，而「可再分发」是另一个维度的事实。
如果哪天真要把词库开源，我这个绿灯是**假绿**。

修正后的优先级是：**公开分发声明（能不能再分发 / 要不要署名）排在「自有内容豁免」之前**，
因为「自有内容 license 自主」只免除强制 SPDX 要求，**免不了分发声明**。

> 自有内容的 license 自主，意思是**可以选择** MIT，不是**默认** MIT。
> 把"自主"当成"可以随便用"，是这行最常见的误读。

### 词库本身

13 个包 / 9438 条。里面我比较满意的是 5 个技术细分包：
`ai-core`（43 条大模型词汇）、`cloud-native`（30 条 K8s）、
`go-code` / `ts-code`（各 50 条**整行骨架代码**，不是单词列表）、
`frontend`（20 条前端高频词）。

`go-code` / `ts-code` 这个形态是我自己比较喜欢的：练的不是"认识这个单词"，
是"这段代码能不能不看就敲出来"，因为真实写代码时需要的是后者。
比如 `go-code` 里第一条就是 `if err != nil { return err }`。

技术栈是 React 19 + TypeScript + Vite，纯前端、无后端。
仓库在 GitHub（`yqh-core/geek-typing`），词库目录是 `content/vocabulary/`。

## 5. 被删/被降权的话术退路

V2EX **主题一旦有人回复就不可删除**，所以必须提前备好退路。

### 退路 1：换节点重发（最主要手段）

被移动到推广节点或被删后，**不要重发同一个帖子**（会被判 spam）。
换个角度重发：**去掉产品叙述，纯粹当技术笔记发**，标题从"我做了个 X"改成
"关于 Y 的一个工程取舍"，把项目放在最后一句。

- 首发：`分享一个打字背单词的开源项目：词库为什么用 JSON 而不是 SQLite`
- 退路：`词库数据用 JSON 存 + 体积棘轮门禁：一次内容管线被撑爆后的取舍`

### 退路 2：拆条

把内容拆成两个独立技术帖，一个讲许可判定（通用性强，最安全），
一个讲体积棘轮。项目只在最后一句提一次。
**这条路径存活率最高**，因为它本来就不像广告。

### 退路 3：改投其它站

V2EX 不是终点。取证时发现同类内容在中文技术站有大量转载生态：
CSDN、腾讯云开发者社区、阿里云开发者社区、GitCode、博客园、掘金。
可作为二次投放渠道（同样遵循"转载原文 + 超链接"，不做全文搬运）。

### 退路 4：不发了

如果连续两次被删，**停手**。继续试发会被判 spam 降权，
反而影响账号后续所有节点的发帖。改为只做 GitHub 侧沉淀。
