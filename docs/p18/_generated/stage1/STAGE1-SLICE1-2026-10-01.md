## 5.1 顺带补掉判据 5 的一个盲区（提交 `43921c3`）

补上面这批的时候，独立复核发现判据 5（`lazy` 探测串必须命中主 chunk 0 次）**对「代码骨架类」词库包是瞎的**：
`collectLazyProbes` 的 vocabulary 分支只用 `distinctProbes()`，它挑「≥5 个纯字母」的词，而
`ts-code` / `go-code` 的 `word` 字段是整条代码骨架（`const [state, setState] = useState(initialState);`），
**一条都挑不出来** ⇒ 探测数 0 < `PROBE_MIN(3)` ⇒ 判 UNKNOWN ⇒ 本门 UNKNOWN 视为不通过 ⇒ **整门判红**。

⇒ 后果是：现在只要有人把 `ts-code` / `go-code` 改成 lazy，门立刻红，而报错写的是「只找到 0 个独有探测串」，
读代码的人看不出该修哪儿。**这条盲区直接卡着 Stage 2**（新内容包很可能就是代码骨架形态，
门会在加词的那一刻毫无征兆地红），所以先补门、再谈改词库 —— 顺序不能倒。

**处置（commit `43921c3`）**：vocabulary 分支先走主路径，仅当结果 `< PROBE_MIN` 时才用同文件已有的
`asciiPhraseProbes()` 兜底取该包独有的 ASCII 长串，`kind` 增加第三取值 `vocabulary/load/ascii` 让报错能区分路径。
falsify 新增 `L5b`：把 `ts-code` 以 lazy 身份重新喂给真实的 `collectLazyProbes`，
**先断言兜底产出 ≥ `PROBE_MIN` 个串（不够就 Fatal），再把串塞进主 chunk 判红** —— 这条是「兜底路径不是死代码」唯一的机器判据。

实测兜底串（各 8 个，`ts-code` 与 `go-code` 跨包**零重叠**，且 `src/**` 源码里一条都不存在 ⇒ 改 lazy 后主 chunk 必然命中 0）：

```
ts-code: "const [state, setState] = useState(initialState);" / "const sorted = [...list].sort((a, b) => a - b);" …
go-code: "w.Header().Set(\"Content-Type\", \"application/json\")" / "func NewServer(cfg Config) (*Server, error) {" …
```

反直觉的旁证：在**当前 inline 态**先测，这些串在主 chunk 命中 ts-code 7/8、go-code 4/8 —— 这恰恰是「inline 泄漏」的真实信号，
说明兜底串有分辨力，不是主 chunk 里的废串。

**这条留下的两个盲区（下批再说，先记账）**：
1. **兜底不做主 chunk 过滤**：若某个骨架串恰好也被 App 源码写了，干净态就会「部分命中 ⇒ UNKNOWN ⇒ 门红」，
   且报错分不清是「探测串撞源码」还是「包泄漏」。加 `stripOwnPayload` 过滤会让兜底在泄漏态自我阉割 ⇒ 需要拍板，我没擅自改。
2. `asciiPhraseProbes` 会把 `translation` / `definition` 里的 ASCII 字段也当候选 ⇒ **Stage 2 加词库时若带英文 definition，
   兜底串可能来自 definition 而非骨架本身**，探测能过门但「串是不是该包内容特征」这层含义变模糊。

## 8. 对「3c 是产品取舍」这个前提的核实（2026-10-02）

评审人（yqh）第三轮评审判断 3c 属于「首屏直接可用 vs 首屏体积」的产品取舍，因此不该由工程侧擅自决定。
**我核实了这个前提，它对新用户不成立** —— 支撑就三行代码：

```
src/core/content/schema.ts:107   export const DEFAULT_BANK_ID = 'ai-core'
src/hooks/useBank.ts:46          const bank = useMemo(() => banks.find((b) => b.id === bankId) ?? banks[0], …)
src/hooks/useBank.ts:57          setBankWords(bankWordsOf(bank))
```

`useBank` 首屏只解析**一个** active `bankId`，新用户 = `ai-core`；首屏链路（`main.tsx` → `App.tsx:80/82` → `HomePanel`）
只从 manifest 读 `bankName` / `bankCount`，**根本不碰词表**。cet4 / cet6 目前是「以 inline 字符串形式躺在主 chunk 里被静态打包」，
运行期首屏从不去读它。主 chunk 探针也印证：inline 5 包的独有词在主 chunk 里全命中，lazy 5 包全不命中。

⇒ **`DECISIONS-POST-P18.md §9.5.2:286` 那句「代价是 cet4 从"零等待"变成"首屏有骨架屏"，这条我没替你决定，因为它同时是产品取舍」
前提与代码不符** —— 当它写下那句时，`DEFAULT_BANK_ID` 就已经是 `ai-core` 不是 cet4 了（历史记录不重写，此处标注矛盾）。

**唯一让这个取舍「部分成立」的路径也存在，必须单独定性**：

```
src/hooks/useSettings.ts:34   useState(() => readStorage('gt.bank', DEFAULT_BANK_ID))   // 惰性初始化，挂载瞬间读 localStorage
tests/e2e.mjs:1550-1554       setItem('gt.bank','cet4') → reload → waitForTestId('home-panel')   // e2e 实证这条路径
```

| cohort | 首屏 active | cet4/cet6 是否首屏摸到 | 改 lazy 的性质 |
|---|---|---|---|
| 新用户（无 `gt.bank`） | `ai-core` | **否** | **纯工程收益**（raw −21.67 KiB / gzip −8.22 KiB） |
| 存量用户且上次选 cet4/cet6 | `cet4` / `cet6` | **是** | 影响首屏（部分成立），且改 lazy 后这条路径反而是它们的离线兜底 |

另外两条随之澄清的事实：

- **加载态在哪儿（纠正一处提示）**：真正的零词/加载态在 `src/components/Memorize.tsx:270-283`（`memorize-loading` / `memorize-empty` 两个 testid），
  是**一行纯文字** `正在加载词库…`，仓库里没有骨架屏代码。
  `BankManager.tsx:56` 那个是导入 0 词的解析失败提示，不是词库空态。
- **改 lazy 后唯一的真实回归**：离线 + 从未在线切过 cet4/cet6 ⇒ sw 返 504（`public/sw.js:162`）⇒ 词库空。
  把 cet4/cet6 塞进 `WARMUP_IDS` **无效**（`check-bundle.mjs:90` 上限 2，且预热本身就在 `window load` + idle 之后）。

⇒ 结论：**3c 的「产品取舍」标签可以卸掉，只剩一条真取舍 —— 存量用户「离线 + 首次切 cet4/cet6」会空。**
这条是否接受，仍需产品拍板，但它是个**小得多的问题**，不该再拿它把 21.67 KiB 一起押住。

## 9. 顺带查出的一个真缺陷（不依赖 3c，独立成立）

`src/hooks/useBank.ts:61-75` 的 catch 只 `console.warn`，**无重试、无错误态**：

```js
.catch((e) => {
  // 断网首次切到未加载过的大词库：chunk 拉取失败，保持加载态（词库数据无法凭空获得）
  console.warn(`词库 ${bank.id} 加载失败`, e)
})
```

而 `Memorize.tsx:270-283` 把「`bank.load` 存在且 words 为空」一律渲染成 `正在加载词库…`。
⇒ **加载失败时用户永远看到「正在加载词库…」，卡死在那里，没有任何自救入口**（无重试按钮、无错误文案）。

**这条不只影响 3c —— 对已经上线的 `kaoyan` / `toefl`（已是 lazy）同样生效**，即它是一个**已在生产环境里的缺陷**，
不是「为下一刀铺路」的新功能。核实过的边界：`tests/e2e.mjs` **没有**对 `memorize-loading` / `memorize-empty` 的断言
（grep 只命中 `:bank 2` 后 `waitForTestId(page,'word')` 那类正常路径），所以改这个分支不会破坏 171 个用例里的任何一个。

**最小补丁设想**（还没动手，因为涉及 UI 文案，且 N6 未签 —— 按「不擅自动 UX」的纪律摆出来等裁定）：
`useBank` 加一个失败计数/状态 → `Memorize.tsx` 在既有三态上开第四态（保留 `memorize-loading` testid，新增失败态 testid）
→ 补 2 个 i18n key（zh + en，如「词库加载失败，点击重试」）→ 失败态给一次重试入口。
不改 e2e 用例数，不碰成功路径。

**⇒ 三个待裁定的点（都不在第一刀范围内）**：① 3c 那条「离线首次切会空」是否接受；② 上面这个加载失败缺陷现在修 / 列为 N13 独立立项 / 跟着 3c 一起做；③ §7 盲区 ① 走哪条路。
