## 3. N13：修「加载失败永久卡 Loading」

### 3.1 缺陷（复述，便于执行者理解现状）

```ts
// src/hooks/useBank.ts:61-75
useEffect(() => {
  if (bankWordsOf(bank).length > 0) return
  let alive = true
  ensureBankWords(bank)
    .then((w) => { if (alive) setBankWords(w) })
    .catch((e) => {
      // 断网首次切到未加载过的大词库：chunk 拉取失败，保持加载态（词库数据无法凭空获得）
      console.warn(`词库 ${bank.id} 加载失败`, e)
    })
  return () => { alive = false }
}, [bank])
```

而 `src/components/Memorize.tsx:270-283` 把「`bank.load` 存在且 words 为空」一律渲染成 `正在加载词库…`。

⇒ **chunk 拉取失败时，用户永远看到「正在加载词库…」，无重试、无错误文案、无自救入口。**

**这条对已上线的 `kaoyan` / `toefl`（已是 lazy）同样生效** —— 是已在生产环境的缺陷，不是 3c 引入的。
这也是它优先级高于 3a 的原因：Stage 1 在持续扩大 lazy 范围，这条会随范围变大而更常撞。

### 3.2 最小补丁（三处）

**① `src/hooks/useBank.ts`** —— catch 里**记录失败态**，并让 effect 可被重试重跑：

- 加一个 state（例如 `const [failed, setFailed] = useState<ContentPackage | null>(null)`，或等价的最小实现）
- catch 里 `setFailed(bank)` 并保留 `console.warn`（日志别删）
- `.then` 成功后 `setFailed(null)`
- effect 依赖 `[bank]` 加失败态/重试计数，使「失败后重试」能重新发起 `ensureBankWords`
- 换库成功或换到别的库时清除失败态（别让上一个库的失败态粘住新库）

**② `src/components/Memorize.tsx:265-283`** —— 既有三态上**开第四态**，不动前三个 testid：

- `memorize-loading`（`bank.load` 存在 & 空 & 未失败）照旧
- `memorize-empty` 照旧
- **新增**失败态分支，带**新的** `data-testid`（例如 `memorize-load-error`）+ 重试入口（点击可重试当前库）
- 旧注释「三态区分」要改成四态，并写清第四态的触发条件

**③ `src/i18n/zh.ts` + `src/i18n/en.ts`** —— 各补 1–2 个 key（失败文案 + 重试动作），
`zh` 用中文、`en` 用英文，**两个语言文件必须同时加**（只加一个会让另一语言回退到键名）。
参照既有 `memorize.loadingBank` / `memorize.emptyBank`（`zh.ts:256-257` / `en.ts:255-256`）的写法与位置。

## 5.3 本轮最有价值的发现：那个重试按钮是假的

N13 交完先做独立故障注入（CDP `Network.setBlockedURLs(["*words-*.js"])`），实测：

| 阶段 | 点 `memorize-load-retry` 后的网络增量 |
|---|---|
| 仍断网 | `requestWillBeSent` 增量 **0**；`console.warn` 1→2（effect 确实重跑了）；UI 仍 `error=1` |
| **解除阻断后点同一个按钮** | 增量 **0**（决定性证据）；`console.warn` 2→3；UI 仍 `error=1` |
| 同页对同一失败 URL 连 `import()` 两次 | 两次都 `Failed to fetch dynamically imported module`，**0 个网络请求** |
| 手动加 `?retry=1` 再 import | **1 个请求**，成功，11 534 字节 |
| 改 `location.reload()` | 恢复 |

根因：**Chrome 的模块 map 缓存失败条目** —— 取模块失败会把该 URL 条目留在 `fetched` 态、`record = null`，
后续 `import()` 同一个 URL 直接 reject 且不再发请求。⇒ 失败的是同一个 chunk URL 时，页内重试在浏览器层面不可能自愈。
⇒ 那个按钮点了**连转圈都没有**，比不加按钮更糟。

**顺带把「加 cache-busting 打破模块 map」这条路试死了**（独立 Vite 小工程实测三种写法）：

| 写法 | 构建后实际行为 |
|---|---|
| `` import(`...?raw&retry=${n}`) `` | Rollup 把运行时 URL 改成预烘焙 chunk，**query 被吃掉** ⇒ 失效 |
| `import('...?raw' + x)` | 运行时 URL 变 `/assets/words.json?raw&retry=1` ⇒ 404 |
| `const L = (s) => async () => import(s)` | **只剩 index chunk，词表被内联进主 chunk** ⇒ **判据 1 膨胀 + 判据 2 计数塌缩 + 判据 5 反向盲区，三重破门** |

⇒ 唯一又便宜又真的方案是 reload。`0d49550` 把入口改成 `location.reload()`，
重新注入实测：点按钮**新增 4 个请求**（假按钮时代是 0），断网下 reload 后仍是失败态（不伪装成已恢复），
解除阻断后 reload 恢复出词（首词 `eagle`）。文案也改成诚实的：
`zh`「词库加载失败，请检查网络连接」/「刷新页面重试」、`en`「Failed to load the word bank. Check your connection」/「Reload page」。

工程师顺手删了 `retryToken` state —— 入口改成 reload 后没人再触发它，留着就是下一任「假入口」的温床（`grep` 全仓零引用，已核实）。
